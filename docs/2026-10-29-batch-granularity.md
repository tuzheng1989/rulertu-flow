# 批次粒度规则：设计推导与纸面验证

规则的唯一出处是 `plugins/rulertu-flow/skills/optimization-plan/SKILL.md`「批次粒度」节。本文记录推导过程与两份既有方案的纸面重划验证，供维护者重估规则时追溯（2.7.0，2026-10-29）。

## 设计演进（三轮）

1. **合并优先**：根因是 SKILL.md 只定义了"每批长什么样"（五要素、T 级），从未定义"一批应该多大"；既有机制（T 级单一化、回滚边界、并行）都在激励拆小，而每批固定开销（开工检查、委派单、上下文装载、验证、收口）随批次数线性增长。上下文窗口已扩大几个量级，单批可承载多锚点。
2. **收口批次禁令**：波次收口已含全量测试、构建与红线回归，方案再立纯回归收口批是双份职能。收尾改动按规模分流。
3. **上下文流向统一**：上述规则收敛为一个第一性原理——批次间上下文理应连续则合并；批次独立性是质量来源则隔离（基线漂移、验证独立、执行互斥、爆炸半径）；两者皆不涉及的中性情形按 T 级分界。该原则与 dual-model-listening 方案取舍 C（外部模型会话连续/隔离策略）同构。

## 被证伪的备选路径

- **降低每批固定开销（SMED 路线）**：委派单模板化、同波次复用执行代理——当前宿主（Claude Code 子代理每批新上下文、Codex fork 不延续波次）不可行，合并是唯一杠杆；前提已写入规则末句，宿主机制演进时重估。
- **T 级批内分区验证**：批内 T1 部分主控验、T2 部分走审计——复杂化 implement-plan 查表逻辑，审计半个批没有意义。
- **批间接口文档化为通用义务**：前批收口附接口摘要可降低细拆成本，但增加流程义务且解决不了设计意图共享；仅"前批产物大而接口小"形态（如 B4/B5）值得，不立为规则。

# 经验回流机制（distill）需求规格

政策落地后，本机制的运行规则唯一出处迁入对应 SKILL.md，本文退为设计记录。当前状态：需求规格，实施分批方案另立（2026-11-12）。

## 背景与问题

插件的政策文本（各 SKILL.md 的 T 级、派单、验证条款）与 references/roles 角色契约是静态的：写完不再演进。哪些条款真的改变模型行为、哪些是模型本来就会的，没有证据。同时 `.flow-evidence/` 证据目录持续积累审计报告与问题记录，同类缺陷跨方案重复出现却没有回流通道——copyright 整改、flow-deck 各方案的审计报告里，"委派单映射缺失""测试断言改名不翻转"一类问题反复以不同面目出现，每次都靠 Auditor 现场重抓。

外部印证：Google Chrome 的 modern-web-guidance 把"数据驱动修剪"（删掉模型本来就擅长的建议，补强真正易错的地方）作为指南持续有效的核心手段。本机制把同一原则引入 rulertu-flow：流程从固定文本变成有证据回流的学习系统，问题记录从"记档即终点"变成"归纳即输入"。

## 目标

1. **复发判定**：同一缺陷模式在两个及以上独立方案的证据中出现时，可靠识别并归纳为一条模式条目。
2. **回流建议**：每条复发模式产出修订建议，指向明确的政策条款或角色契约位置，附证据引用与修订草案。
3. **精简候选**：长期未触发的政策条款被标记为候选精简，附扫描口径与负面证据的局限说明。
4. **人审门**：回流不直接修改 SKILL.md 与 references。产出建议卡与账本条目，经用户确认后按既有 commit 流程落地。

## 非目标

- 不建检索基础设施。语义检索路由是另一条设计线，本机制只用文档聚类。
- 不强制上游结构化。审计报告保持自由文本，P 级分级沿用既有惯例（`[P2] 文件:行号 描述`），聚类在回流时进行。
- 不自动修订任何文件。一切产出是建议，落地必经人审。
- 不处理项目级局部经验。单项目经验留在该项目证据目录，本机制只产出插件级（政策与角色契约）修订建议。

## 核心概念

| 概念 | 定义 |
|---|---|
| 缺陷模式 | 跨批次可复述的一类问题，如"委派单的改动锚点与测试命令映射不可信""T 级低估致验证强度缺位" |
| 复发 | 同一缺陷模式在两个及以上不同方案的证据中各出现至少一次 |
| 回流账本 | `docs/lessons-ledger.md`：模式名、证据引用、修订对象、处置状态（候选 / 采纳 / 拒绝 / 已落地）的累积台账 |
| 精简候选 | 距上次触发超过阈值 N 个波次的政策条款或角色契约节 |

## 功能需求

### 输入

1. 方案集合的证据目录（默认：仓库内全部 `.flow-evidence/`；跨项目使用时由调用者指定目录）。
2. plan-iterate 评审留痕（`.plan-iterate/` 的问题清单部分）。
3. 现行政策全文（各技能 SKILL.md、references/roles/）。

### 归纳流程

1. **收集**：提取证据中的问题记录。P0/P1 必收；P2 默认不收，噪声太高，显式开关才纳入。
2. **聚类**：按缺陷内容聚类，不按文件或批次。逐簇给出模式名、覆盖证据清单、复现描述。
3. **判定**：单方案孤立问题不回流；跨方案复发才成条目。判定依据写入条目，可追溯。
4. **产出建议卡**：每条含五要素——模式名、证据引用（方案、批次、文件）、修订对象（哪个 SKILL.md 哪节，或哪篇角色契约）、修订草案、置信说明（证据强度与反例）。
5. **精简扫描**：对照账本与证据扫描现行条款，距上次触发超过阈值 N 的列候选。扫描不到不等于无效，候选条目必须写明这一局限，由人裁决。

### 落盘与落地

1. 建议卡写入回流账本 `docs/lessons-ledger.md`，状态置"候选"。
2. 用户确认采纳后，按建议卡草案修订政策文本，commit 文案经 `rulertu-flow:commit` 起草，账本条目关闭为"已落地"。
3. 拒绝的条目保留在账本，状态置"拒绝"并记一句理由，防止同一模式被反复提出。

### 流程集成点

1. **波次收口提醒**：收口报告中证据目录存在未消化的 P0/P1 时，附一句"可运行 distill 归纳"。仅提醒，不自动运行。
2. **与 plan-iterate 的分工**：distill 是跨方案视角，plan-iterate 是单方案评审，互不替代。distill 可建议对某方案补一轮对抗评审。
3. **与 issue tracker 的分工**：代码缺陷走 GitHub Issues；distill 只处理流程与政策缺陷。

## 设计取舍

| 取舍点 | 决定 | 被证伪的备选 |
|---|---|---|
| 执行载体 | 独立技能 `distill` | 波次收口附带归纳：单波次只有本波次证据，凑不满"跨方案复发"的判定视野；收口也已够重 |
| 触发方式 | 用户显式调用 | 收口自动归纳：高智能密度动作自动执行与"不静默降级"哲学相悖，且每波次运行的上下文成本不可控 |
| 上游契约 | 不强制审计报告结构化 | 给 Auditor 立发现清单 schema：改造三个角色的输出契约，收益撑不起改造面，自由文本加 LLM 聚类已够 |
| 人审门 | 必经 | 直接修订 references：错误归纳会被后续所有实施放大，无人审的回流是负资产 |
| 修剪方向 | 增删并重 | 只增不删：上下文单调膨胀，与"删冗余补弱项"的原始启示相悖 |

## 验收标准

1. 用 `plans/copyright-skills/evidence/` 真实数据回放：给定含同类问题的两个波次证据目录，归纳结果聚为一簇，模式名可读，证据引用可逐条点验。
2. 注入一个仅单方案出现的问题，不产生回流条目。
3. 每条建议卡五要素齐备，缺任何一项即不合格。
4. 精简候选附扫描口径与局限说明；无证据支撑的"该条无效"结论不出现。
5. 全程只写账本与建议卡，SKILL.md 与 references 零改动。
6. 回放数据上 P2 默认关闭时，噪声条目数量可控（不淹没 P0/P1 条目）。

## 开放问题

1. 精简阈值 N：建议 6 个波次起步，积累三个月运行数据后再校准。
2. 重政策条款的修订是否过一轮 plan-iterate 对抗评审：倾向"动 T 级或验证强度的要，加角色契约细节的不要"。
3. 账本放 `docs/` 还是 `plans/rulertu-flow/`：倾向 `docs/`（跨方案的维护者视角，与本文档同级）。
4. 跨项目场景：其他项目仓库的证据目录如何接入（复制抽样、还是 distill 支持外部路径参数），实施时定。

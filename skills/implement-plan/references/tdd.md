# 测试驱动开发

TDD 是“红 → 绿”的小步循环。本参考规定如何写出值得长期保留的测试：好测试的标准、测试落点、反模式和循环纪律。每轮实现前和执行中都要遵守，而不是完成后再补。

探索代码库时，如存在 `CONTEXT.md`，先读取它，使测试名称和接口词汇与项目领域语言一致；同时遵守改动区域内的 ADR。

## 好测试的标准

测试通过公开接口验证行为，不验证实现细节。实现可以彻底重构，测试不应因此变化。好测试读起来像规格，例如“有效购物车可以结账”，明确说明系统具备什么能力，并且不依赖内部结构。

示例见 [tests.md](tests.md)，mock 规则见 [mocking.md](mocking.md)。

## 接缝：测试应落在哪里

**Seam（接缝）**是测试观察行为的公开边界：从接口观察结果，而不伸入内部。测试写在接缝上，不直接绑定内部实现。

**只测试预先确认的接缝。** 写测试前先列出本轮要测试的接缝，并在任务契约中确认。不能在未确认的接缝上新增测试。测试不可能覆盖一切；先确定接缝，才能把投入集中在关键路径和复杂逻辑，而不是平均散落到所有边角。

需要确认的问题是：“公开接口是什么，本轮应测试哪些接缝？”

如果接口形状本身仍不明确，例如模块应该多深、接缝放在哪里、接口应暴露什么，则读取 [代码库设计](codebase-design.md)。它定义模块、接口、深度、接缝、适配器、杠杆和局部性等共同词汇，只作为按需参考，不另起一轮流程。

## 反模式

- **与实现耦合**：mock 内部协作者、测试私有方法，或绕过接口从旁路验证，例如直接查询数据库。识别信号是：行为没变，仅重构实现就导致测试失败。
- **同义反复**：断言用与实现相同的方法重新计算期望值，例如 `expect(add(a, b)).toBe(a + b)`。这种测试按构造必然通过。期望值必须来自独立真值，例如已知字面量、手算示例或规格。
- **水平切片**：先写完全部测试，再统一实现。这会验证想象中的结构，并在理解实现前锁死测试形状。改用**垂直切片**：一个测试 → 最小实现 → 重复；每个测试都是根据上一轮反馈调整方向的“曳光弹”。

## 循环纪律

- **先红后绿**：先写会失败的测试，再写刚好足以通过的代码；不提前实现未来用例，不添加推测性功能。
- **每次一个切片**：每轮只处理一个接缝、一个测试和一个最小实现。
- **重构不属于红绿循环**：重构放在评审阶段，不混入“红 → 绿”的实现循环。

# 代码库设计

设计**深模块**：用较小接口承载大量行为，把接口放在清晰 seam 上，并通过该接口测试。目标是让调用方获得杠杆、让维护者获得局部性、让测试拥有稳定表面。

## 术语表

以下术语应保持一致，不随意替换为“组件”“服务”“API”或“边界”。统一词汇本身就是本参考的价值。

**模块（Module）**：任何同时具有接口和实现的对象，刻意不限定规模，可以是函数、类、包或跨层切片。

**接口（Interface）**：调用方正确使用模块时必须知道的一切，包括类型签名、不变量、顺序约束、错误模式、必需配置和性能特征。这里的“接口”比 TypeScript `interface` 或方法签名更宽。

**实现（Implementation）**：模块内部的代码。它不同于**适配器**：讨论 seam 上承担什么角色时用“适配器”，讨论模块内部内容时用“实现”。

**深度（Depth）**：接口提供的杠杆，即调用方或测试每学习一单位接口能够驱动多少行为。小接口背后承载大量行为就是深模块；接口复杂度几乎等于实现复杂度就是浅模块。

**Seam（接缝）**：无需在该位置编辑代码就能改变行为的地方，也是模块接口所在的位置。seam 放在哪里，与 seam 后面放什么，是两个独立设计决策。避免用“边界”替代，以免与 DDD 的限界上下文混淆。

**适配器（Adapter）**：在某个 seam 上满足接口的具体对象。它描述角色，即填补什么插槽，而不是描述内部材料。

**杠杆（Leverage）**：调用方从深度获得的收益；学习较少接口即可获得更多能力，一份实现可服务多个调用点和测试。

**局部性（Locality）**：维护者从深度获得的收益；变更、缺陷、知识和验证集中在一个地方，而不是散落到所有调用方。修一次，处处生效。

## 深模块与浅模块

深模块 = 小接口 + 大量实现：

```text
┌─────────────────────┐
│       小接口        │  ← 方法少、参数简单
├─────────────────────┤
│                     │
│       深实现        │  ← 隐藏复杂逻辑
│                     │
└─────────────────────┘
```

浅模块 = 大接口 + 少量实现，应尽量避免：

```text
┌─────────────────────────────────┐
│             大接口              │  ← 方法多、参数复杂
├─────────────────────────────────┤
│             薄实现              │  ← 仅做透传
└─────────────────────────────────┘
```

设计接口时询问：

- 能否减少方法数量？
- 能否简化参数？
- 能否把更多复杂性隐藏在内部？

## 原则

- **深度是接口的属性，不是实现的属性。** 深模块内部仍可由小型、可替换部分组成，只是这些部分不属于外部接口。模块既可以拥有实现私有的内部 seam，也可以在接口处拥有外部 seam。
- **删除测试。** 想象删除这个模块：如果复杂性随之消失，它很可能只是透传；如果复杂性重新散落到多个调用方，它正在发挥价值。
- **接口就是测试表面。** 调用方和测试跨越同一个 seam。如果测试总想越过接口，模块形状很可能不合理。
- **一个适配器只是设想中的 seam，两个适配器才形成真实 seam。** 只有确实存在变化时才引入 seam。

## 面向可测试性的设计

1. **接收依赖，不在内部创建依赖。**

   ```typescript
   // 易测试
   function processOrder(order, paymentGateway) {}

   // 难测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，减少隐式副作用。**

   ```typescript
   // 易测试
   function calculateDiscount(cart): Discount {}

   // 难测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **保持较小表面。** 方法越少，需要的测试越少；参数越少，测试准备越简单。

## 关系

- 一个模块对调用方呈现一个接口；
- 深度是模块相对于其接口的属性；
- seam 是模块接口所在的位置；
- 适配器位于 seam 上并满足接口；
- 深度为调用方产生杠杆，为维护者产生局部性。

## 不采用的表述

- **用实现行数与接口行数之比衡量深度**：这会奖励填充实现代码；本参考采用“深度即杠杆”。
- **把接口限定为语言关键字或公开方法**：范围过窄，接口包含调用方必须知道的全部事实。
- **使用“边界”一词**：容易与 DDD 限界上下文混淆，应使用 seam 或接口。

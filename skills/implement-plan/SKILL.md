# 实施方案 · 分批执行工作流

## 定位

本技能是执行侧规则的**唯一出处**：optimization-plan 只管如何写方案，plan-iterate 只管如何评审方案文档，本技能负责把定稿方案落地。何时派执行代理、何时派审计代理、何时运行 Codex、何时收口，都按批次 T 级查表执行，不留给主控临场判断。

## 触发边界

- **触发**：执行一份含 T0-T3 定级的分批实施计划（通常由 optimization-plan 产出，或 plan 内自带分级流程章节）。
- **不触发**：单票小改（无 plan 文件，走「读代码锚点 → TDD 红绿 → 红线回归」）。

## 角色与职责

- **主控**：当前会话的主代理，负责派单、机械验证和收口。T1 及以上不亲自写实现代码，也不以执行代理的文字回报替代实测。
- **执行代理**（`rulertu-flow:executor`）：接收主控已分解好的单个批次，包括目标、验收标准、边界和实现方法；专注实施并回报实际改动、可见状态、产物路径和剩余问题。
- **审计代理**（`rulertu-flow:auditor`）：只读独立验证者。不信任执行代理回报，亲自重跑证据包内命令、重读完整差异并核验锚点；逐条输出 PASS/FAIL，只报告不修复。
- **Codex**（仅 T3）：以 `codex exec` 在只读沙箱中提供第二意见，核对代码差异与计划符合度，寻找未覆盖路径和设计漏洞。

## 内部参考加载规则

- 每个 T0 批次开工前，以及每次准备执行代理委派单时，主控必须读取 [测试驱动开发](references/tdd.md)，把本批次的接缝、红绿循环和验证纪律写入委派单的“实现方法”。
- 如果接缝、模块接口或依赖注入位置尚未确定，主控在派单前读取 [代码库设计](references/codebase-design.md)；需要合并浅模块时再读 [深化模块](references/deepening.md)，需要比较多个接口候选时再读 [设计两次](references/design-it-twice.md)。
- 接缝未确认时不得派执行代理。执行代理只负责在已确认接缝上实现，不承担重新设计整个模块的职责。
- 测试示例和测试替身规则分别按需读取 [好测试与坏测试](references/tests.md) 与 [何时使用测试替身](references/mocking.md)。

## 开工检查点（每批次开工前，强制）

动手前主控必须**先复述后执行**，防止上下文压缩后凭印象执行：

1. 读该批次详案，摘出：**T 级 + 定级依据 + 派单流程 + 验收标准清单**；
2. 向用户输出一行开工声明，例如“B3 · T3 · 执行代理 → 审计代理 → Codex，验收 N 条”；
3. 核对该批依赖的前置批次已收口（查证据目录，见下）。

未完成检查点不得开工。

## 分级执行流程（查表，无裁量）

| 级 | 谁实施 | 验证收口 |
|---|---|---|
| **T0** | 主控（单文件小改、无契约邻近） | 锚点 → TDD 红绿 → 红线回归（无子代理） |
| **T1** | **执行代理** | 主控亲自机械验证收口，无审计代理 |
| **T2** | **执行代理** | 审计代理（证据包模式） |
| **T3** | **执行代理** | 审计代理（证据包）→ Codex 第二意见，三者全 PASS 才算完成 |

硬规则：

- **T1 及以上禁止主控亲自实现**——「觉得简单就自己写」是本流程要防的首要失效模式；
- **T2/T3 必派 auditor**、**T3 必跑 codex**，不因批次「看起来小」而降级省略；
- 执行中发现实际改动超出定级假设（如 T1 批改到了契约文件），立即升级重走该级流程；
- 任一必查项 FAIL → 批次阻断，executor 修复后**重新走完整流程**（不接受只补 FAIL 项的局部重验）；T3 的 codex FAIL 视为批次未完成（即使 auditor 已 PASS）。

## 执行代理派单规格

委派单必须自包含，executor 不自行检索全 plan：

1. **目标**：正向表述该批次要达成的行为（禁令只留工具坑类硬护栏）；
2. **验收标准**：plan 中该批的可断言清单原文摘录；
3. **边界**：`文件:行号` 锚点 + 改动要点 + 明确不做什么；
4. **验证命令**：plan 中该批指定的分层测试命令（L1/L2/L3 + 红线回归）。
5. **实现方法**：从内部 TDD 参考提取本批适用的接缝、先红后绿、单切片循环和测试替身边界；只打包本批需要的规则，不复制无关参考。

文件不重叠的独立批次可并行派多个 executor，但**验收/测试不与另一实施 executor 并行跑同一工作区**。

## 主控机械验证纪律（T1 收口方式 / 各级派 auditor 前的抽查）

主控亲自做**机械验证**（跑指定测试命令、读 diff、逐字节对比）——这不是写代码，不违反"主控只调度"。铁律是**结论级输出，不是内容级**，控制主控上下文占用：

- 跑测试：`pytest tests/test_x.py -q | tail -5` —— 只留 exit code + 尾部几行；
- 读 diff：`git diff --stat` 看范围，只对**存疑 hunk** 定向读；需要通读几千行 diff 时说明这已是判断验收，应派 auditor；
- 逐字节对比：`git diff --exit-code` / `cmp`，返回码说话，零内容进上下文。

## 审计代理证据包规格（T2/T3 派单方式）

主控委派 auditor 时，委派单**必须打包**以下内容，auditor 不再自行检索全 plan/代码库：

1. 验收标准清单（原文摘录，含限制性语言）；
2. `git diff` 范围（`--stat` + 涉及文件）；
3. executor 回报原文；
4. **测试结果证据**（供采信）——executor 已跑测试的 exit code + 关键输出（如 `pytest -q | tail -5`，保留 passed/failed 数）；**必须先抽查验证**；
5. 建议重跑的定向测试命令清单（仅在抽查时用）。

**抽查纪律**（主控在派 auditor 前执行）：

- 从 executor 跑过的测试中**定向抽查 1-2 条**（优先选与验收标准直接锚点的），亲自重跑确认 exit code 一致；
- 若抽查通过，打包「测试结果证据」给 auditor 并标注「**已抽查验证，可采信**」——auditor 默认采信，只抽样复查；
- 若抽查失败，派 auditor 时标注「**未抽查验证，需定向重跑**」——auditor 按定向重跑模式逐条重验；
- 抽查成本：每条几百 token 级，只跑关键锚点的，不跑全量。

## Codex 第二意见（仅 T3）

auditor 之外，把「验收标准清单 + diff + executor 回报」交给 codex 做**跨模型**第二意见：契约是否被弱化、是否存在 auditor 与 executor **同模型共有的盲区**。

- 调用：`codex exec`（read-only 沙箱），一条 Bash 后台调用；
- 输出**markdown 结论**（不要 `--output-schema` JSON——经代理会字段漂移）；
- 产出与 auditor 结论并列呈给主控决策，不自动否决；
- 前置：本机 codex 未安装或认证不可用时，**显式告知用户跳过及原因**，不得静默略过。

## 证据落盘即进度（跨会话续传）

- auditor 报告 + 命令输出存档写入 plan 指定的证据目录（如 `.wayfinder/<项目>/evidence/<批次>/`；目录不存在时由首个产出证据的批次创建，随目录放置 `README.md` 确保入库）；
- 结论一行回写 plan 的进度记录（或项目指定的基线文档）；
- **续会话时**：扫证据目录 + plan 勾选状态确定已完成批次与下一批，**不依赖会话记忆**；
- 通过门槛 = 验收标准逐条 PASS + 红线全绿 + 无未声明偏离；证据缺完整输出原文 = 该项 FAIL。

## 波次组织与收口

- 按独立性/依赖分波次执行（依 plan 的波次依赖图）；
- **波次末统一收口**（不是每批）：
  1. **红线回归**：全量测试 + 项目红线（主控或委派，按项目标准）；
  2. **累积 diff 质量评审**：对本波次全部批次合并 diff 审一次。载体优先级：
     - `ocr review`（open-code-review CLI）——**前提：已安装且 `ocr llm test` 通过**。本机认证走 Claude Code env（`ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN` 已在环境），但缺 `ANTHROPIC_MODEL`，**必须单次调用前缀注入，勿持久化**（会连 Claude Code 本体选型一起改掉）：
       ```bash
       ANTHROPIC_MODEL=glm-5.3 ocr review
       ```
       先跑 `ANTHROPIC_MODEL=glm-5.3 ocr llm test` 确认后端通。
     - fallback：未安装 ocr 或 llm test 不通时，用内置 `/review` 命令评审同范围 diff。
  3. **T3 批次例外**：每批已单独加审（auditor + codex），波次末只需覆盖其余批次的合并 diff。
- 评审问题分级处置：**P0/P1**（正确性/契约破坏）派 executor 修 + 复验；**P2**（风格/建议）只记档进 plan 的 Code-Review 节，不阻塞、留下一轮方案消化。

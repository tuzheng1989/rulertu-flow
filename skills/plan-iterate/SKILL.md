# 方案迭代（Codex 评审 → 子代理修复 → 复审）

把方案文档放入“外部评审 → 修复 → 复审”循环，直到质量达标。评审方是 Codex CLI，它以独立上下文读取仓库并验证方案锚点；修复方是当前环境可用的执行子代理。Codex 会话跨轮保留上下文，复审时能够逐条核对上轮问题。

**仓库访问边界**（已写入评审脚本提示词）：代码与事实用于核验方案声明的真伪，包括锚点、既有设施和依赖，失实记 P0；规范与基线，例如 `AGENTS.md`、路线图和进度文档，不作为否决未来方案的依据。涉及基线变更时，只审查是否显式、穿透是否完整，不判断是否应该变更。派发修复任务时必须传递同一口径。

## 前置检查

1. **Codex CLI 可用**：`codex --version` 能正常运行。不可用时停止，并告知用户安装或登录 Codex。
2. **定位方案文件**：优先使用用户参数中的路径；未提供时从当前会话寻找刚产出的方案、计划文件或 `docs/optimization-plan-*.md`；仍不确定就询问用户，不得猜测。
3. **定位评审脚本**：脚本随插件安装。在 Claude Code 中优先使用 `${CLAUDE_PLUGIN_ROOT}`；未注入时，使用下方命令探测本机插件缓存中的最高版本目录。

## 产出目录

所有中间产物放在 plan 同目录下：`<plan所在目录>/.plan-iterate/<plan文件名去后缀>/`

- `review-R1.json` `review-R2.json` … — 各轮评审结果（schema 见 `scripts/review-schema.json`）
- `review-R*.json.log` — codex 完整输出（排障用）
- `session.txt` — codex 会话 ID（复审续接用）

## 流程

### 第 1 轮：发起评审

使用 Bash 后台运行。评审需要读取代码验证锚点，可能耗时数分钟，不要使用前台短超时。

```bash
bash "${CLAUDE_PLUGIN_ROOT:-$(ls -d "$HOME"/.claude/plugins/cache/rulertu-flow/rulertu-flow/*/skills/plan-iterate | sort -V | tail -1)}/scripts/codex-review.sh" "<plan绝对路径>" "<产出目录>/review-R1.json"
```

脚本成功后在标准输出打印 `SESSION_ID=<uuid>`。立即写入 `session.txt`；这是跨轮保持 Codex 上下文的凭据，丢失后只能重开评审。

读取 `review-R1.json`，向用户简要转述：总分、P0/P1/P2 各几条、问题要点。

### 判定是否达标

- **达标**：`score ≥ 8.5` 且 `issues` 中无 P0/P1 → 跳到「汇总报告」。
- **未达标**：进入修复，默认最多 3 轮（用户在指令中另行指定阈值/轮数时从其指定）。

### 修复：派子代理

使用当前环境的委派能力派出 **executor** 子代理（优先使用 `rulertu-flow:executor`；没有该代理类型时使用任一执行子代理）。只提供方案路径和本轮问题清单，让它专注修订文档：

```
修复方案文档 <plan绝对路径>，按以下评审问题逐条修复（评审方：codex）：

P0/P1 问题（必须解决）：
- [P0] <title>：<detail>；修复建议：<suggestion>
- ...
P2 问题（酌情采纳，判断不合理的可跳过并说明理由）：
- ...

要求：
- 只修改这一个 plan 文档，不动任何代码/其他文件
- 每条 P0/P1 都要在文档中有实质响应（修正内容或补充论证），不是只改措辞
- 修复中新增的锚点必须真实存在；优先用代码图谱核实，不可用时使用当前环境的文件读取与文本搜索能力
- 回报：每条问题的处理方式（已修/部分修/不采纳+理由）
```

子代理回报后，将其处理摘要如实转达用户。

### 第 N 轮：续会话复审

```bash
bash "${CLAUDE_PLUGIN_ROOT:-$(ls -d "$HOME"/.claude/plugins/cache/rulertu-flow/rulertu-flow/*/skills/plan-iterate | sort -V | tail -1)}/scripts/codex-review.sh" "<plan绝对路径>" "<产出目录>/review-RN.json" "$(cat <产出目录>/session.txt)"
```

脚本会用复审提示词调用 `codex exec resume`。Codex 保留上轮上下文，并逐条核对问题是否真正解决。完成后回到“判定是否达标”。

### 汇总报告（无论是否达标都要给）

| 轮次 | 评分 | P0 | P1 | P2 | 备注 |
|---|---|---|---|---|---|
| R1 | 7.0 | 2 | 3 | 4 | ... |
| R2 | 8.8 | 0 | 0 | 1 | 达标 ✓ |

加上：最终 `overall_quality` 摘要、仍遗留的 P2 清单、每轮修复的对应关系。评审 JSON 都在产出目录，用户可自行查阅。

## 异常处理

- **codex 调用失败**（脚本退出码 3，多为网络/配额问题）：看 `.log` 排因；重试 1 次，仍失败则停止循环，向用户报告已完成的轮次与产物位置。若首轮已成功，`session.txt` 还在，用户网络恢复后重新触发本 skill 可从复审继续（把已有 review JSON 作为上文，直接走第 N 轮）。
- **轮数用尽仍未达标**：如实报告差距（差在哪些 P0/P1），不要为凑达标替 codex 打分或擅自宣布通过。
- **评审明显跑偏**（如 codex 评的是旧版本内容）：确认子代理确实保存了修改、复审命令带对了 session_id，再重跑该轮。

## 边界

- 本技能只迭代**方案文档**。用户要评审代码差异时，改用当前环境的代码评审能力或 `codex review`。
- Codex 全程运行在只读沙箱；唯一允许修改的是方案文档，由修复子代理完成。
- 评分与问题分级以 Codex 输出为准，主控不代评，也不修饰分数。

# 第 2 章 · 上下文工程（全书最关键章）

> 来源：原书第 2 章。衍生解释，非逐字原文。

## 核心问题
给模型看什么、怎么组织——这比模型本身多聪明更影响结果。如何工程化管理上下文？

## 核心观点
- **上下文决定能力上限**。「上下文就是消息列表」是地基。
- API 消息结构定义上下文骨架；KV Cache 约束能改什么；提示工程与 Skills 决定如何高效提供静态指令与动态知识；状态栏把隐式状态变显式元信息；压缩解决上下文膨胀。
- 共同点：**显式、工程化的知识管理**——主动提供提炼过的结构化知识，不让模型被动在海量信息中检索。
- 呼应 Sutton《苦涩的教训》：能更有效利用算力的通用方法最终胜出。

## 关键概念
- **KV Cache**：大模型推理中复用历史计算；约束上下文布局——前缀稳定才能命中缓存，改前缀则缓存失效。
- **提示工程**：流程化设计、工具描述、业务规则细化；以及提示注入（Prompt Injection）攻防。
- **Agent Skills**：动态按需加载提示词，解决提示词无限膨胀（早于 Skill 概念流行，作者团队已用动态加载提示词解决该问题）。
- **Agent 状态栏**：让 Agent 感知执行环境、用户时间 / 工作状态；API 层用 user 角色（无元信息角色），语义上是元信息注解。
- **上下文压缩**：不仅是控制长度，更是通过主动总结把原始数据变成高密度结构化知识（上下文感知压缩）。
- **上下文五部分**：静态前缀框架；本章在其骨架上填血肉，不推翻它。

## 权衡与反例
- KV Cache 友好性与布局灵活性冲突（修改前缀会失效）。
- 压缩有信息损失风险，需主动结构化总结而非简单截断。

## 与其他章节关系

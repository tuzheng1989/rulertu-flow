# Generator-Verifier (生成器-验证器) 模式详解

> ⚠️ **书外工程实践**，非《深入理解 AI Agent》（李博杰）本书内容。
> 属 ai-agent-design pack 的 **practices 实践层**（第五组件），收纳工程社区的 agent 协调模式。
> **书内互补**（非重复）：`proposer-reviewer` method 讲「验证器是瓶颈 / 三类过早终止」的**原理**（扎根 ch4/ch5/ch10）；本章讲生成器-验证器的**工程实现、反馈机制与扩展变体**。

## 概述

这是最简单的多智能体模式之一。一个生成器接收任务并产生初始输出，验证器评估输出是否符合标准，循环直到验证通过或达到最大迭代次数。

## 架构图

```
用户任务
  ↓
┌─────────────┐
│  Generator   │ ← 生成初始输出
└─────────────┘
      ↓ 输出
┌─────────────┐
│  Verifier    │ ← 评估输出
└─────────────┘
      ↓
   ┌──────┴──────┐
   ↓              ↓
接受            拒绝
   ↓              ↓
  完成        ┌─────┴─────┐
              │  Feedback  │
              └────────────┘
                   ↓ (循环)
            ┌─────────────┐
            │  Generator   │
            └─────────────┘
```

## 工作流程

1. **生成阶段**: Generator 接收用户任务，使用领域知识和上下文生成初始输出
2. **验证阶段**: Verifier 根据预设标准评估输出质量
3. **决策阶段**:
   - 通过: 返回最终输出给用户
   - 未通过: 返回具体反馈给 Generator
4. **迭代**: Generator 根据反馈改进输出，回到步骤 2
5. **终止**: 达到最大迭代次数时，返回最佳结果或升级人工处理

## 适用场景

### 典型用例

| 场景 | Generator | Verifier | 评估标准 |
|------|-----------|-----------|----------|
| **代码生成** | 编写代码 | 编写并运行测试 | 测试通过 |
| **邮件回复** | 生成回复 | 检查知识库、品牌指南 | 准确性、语气、完整性 |
| **事实核查** | 生成陈述 | 对比权威来源 | 事实正确性 |
| **合规验证** | 生成建议 | 对照法规文档 | 合规性 |
| **评分** | 生成评分 | 应用评分标准 | 一致性、公正性 |

### 最佳使用条件

✅ 输出质量要求高且评估标准可以明确化
✅ 错误输出成本显著高于额外生成周期
✅ 生成和验证是可分离的技能
✅ 有明确的通过/失败标准

### 不适合的情况

❌ 评估创造性工作的难度与生成相当
❌ 无法明确定义评估标准
❌ 反馈难以具体化（如"这不够好"）

## 关键设计考虑

### 1. 验证标准设计

**糟糕的标准**:
```
"检查输出是否好"
```

**良好的标准**:
```
检查以下条件:
1. 所有用户问题都已回应
2. 技术术语使用正确
3. 引用了具体的产品文档章节
4. 语气符合品牌指南（友好、专业）
5. 没有提供未经验证的功能承诺
```

### 2. 反馈机制

验证器必须返回**具体、可操作的反馈**，而非模糊的批评:

| 模糊反馈 | 具体反馈 |
|---------|----------|
| "代码有问题" | "第 45 行存在空指针风险: 变量 x 可能为 None" |
| "回答不完整" | "未回答第二个问题: 如何处理并发冲突？" |
| "语气不对" | "回复使用了过于随意的语言, 应改为更正式的表达" |

### 3. 终止条件

必须防止无限循环:

```python
MAX_ITERATIONS = 3
FALLBACK_STRATEGIES = [
    "return_best_effort_with_warnings",
    "escalate_to_human",
    "provide_alternatives",
]
```

## 使用 DeepAgents 创建示例

使用 deepagents skill 可以创建这样的结构:

```
创建两个 agent:
- generator:
  prompt: "生成一个 {task_description} 的解决方案"
  context: "使用以下资源: {knowledge_base}"

- verifier:
  prompt: "验证输出是否符合以下标准: {criteria}"
  context: "检查清单: {checklist}"
  当验证失败时: "返回具体反馈: {feedback_format}"
```

## 常见陷阱

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 验证器盲目通过 | 标准太模糊 | 定义明确的通过条件 |
| 循环无法收敛 | 反馈难以实现 | 分析失败模式，调整生成策略 |
| 迭代过多 | 标准过于严格 | 设置合理的迭代上限 |
| 输出退化 | 过度修正导致偏离原始目标 | 记录初始意图，定期对齐 |

## 扩展变体

### 双验证器模式

使用两个验证器分别检查不同方面:
- Technical Verifier: 技术正确性
- Style Verifier: 风格和语气

### 多候选竞争

生成器创建多个候选，验证器选择最佳:
```
Generator → 输出 A, B, C
Verifier → 评分后选择最佳
```

### 自我改进循环

验证器本身也是生成器的一部分:
```
Generator → 输出
Verifier → 检查问题
Generator → 修复问题
Verifier → 最终验证
```

## 指标监控

- 通过率: 需要多少次迭代才能通过？
- 反馈质量: 多少反馈能带来改进？
- 时间成本: 总耗时 vs 单次生成
- 令牌效率: 每次改进的令牌消耗

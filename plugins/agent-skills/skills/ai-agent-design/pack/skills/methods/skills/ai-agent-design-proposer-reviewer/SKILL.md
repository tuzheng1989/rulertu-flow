# 提议者-审核者（proposer-reviewer）· 任务完成判定闭环

## I · 这是什么
让 Agent 审阅自己输出的交付件并迭代改进，**由验证而不是模型自己的感觉决定任务何时结束**。提议方产出结果，独立验证环节对照真实观测审核。核心立场：**循环的瓶颈在验证器**。

## A2 · 解决的三类过早终止
1. **偷懒式假完成**：闭环没走完就宣称「已办妥」。
2. **过早放弃**：一条路走不通就宣布「办不了」。
3. **假成功**：宣称成功但实际未达成。

## 何时用（触发）
- 长流程、高风险任务（金钱、不可逆操作）。
- 执行工具的安全防护（事前审批 + 事后验证）。
- 多 Agent 协作中判定任务完成。
- 生成式内容质检（ch5 多媒体生成）。

## E · 如何实现
1. 提议者产出交付件。
2. 审核者对照**真实观测**验证（不靠模型自宣称）：代码执行结果、视觉渲染截图、工具验证输出、独立检查。
3. 未通过 → 反馈提议者迭代，回 1。
4. 完成标准：验证器确认满足可观测验收标准。
5. 判停：最大迭代次数；验证器明确判定无法达成时报告失败（而非假成功）。

## R · 证据
- 引言：作者团队早于 loop engineering 流行，就用 proposer-reviewer 解决过早认为任务完成的问题。
- ch4 执行工具：层次化安全防护、提议者-审核者审查（事前审批 + 事后验证）、Sidecar。
- ch5：多媒体生成通过 proposer-reviewer 创建 PPT / 视频。
- ch10：Loop 工程「循环的瓶颈在验证器」；多 Agent 优势在于 Reviewer 获得外部反馈（代码执行 / 视觉截图 / 工具验证）。

## A1 · 书中案例
- Pine 处理金钱 / 长程任务（引言）：几十轮交涉，任何一步出错真金白银损失，倒逼出此机制。
- ch10 准则：协作引入新信息才有效——验证器获得外部反馈是关键。

## B · 不适用与边界
- 简单单轮任务无需。
- 验证器必须扎根真实观测；若只是模型再想一遍（无新信息）则无效（ch10 辩论模式反例）。
- 兄弟 skill：完成判定用本方法；推进循环用 react-loop；系统级度量用 eval-driven-iteration。

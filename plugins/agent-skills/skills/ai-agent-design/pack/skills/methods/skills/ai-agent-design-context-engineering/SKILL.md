# 上下文工程 · 决定 Agent 能力上限

## I · 这是什么
**给模型看什么、怎么组织，比模型本身多聪明更影响结果。** 上下文 = 静态前缀（系统提示词 + 工具定义）+ 动态轨迹（消息历史）。核心原则：主动提供提炼过的结构化知识，不让模型被动在海量信息中检索。

## E · 五项核心技术
1. **KV Cache 友好布局**：前缀稳定才能命中缓存；动态内容放后段，改前缀 = 缓存失效。
2. **提示工程**：流程化设计、工具描述规范、业务规则细化；含提示注入攻防。
3. **Agent Skills 按需加载**：把提示词组织成技能文件，按需动态加载，解决提示词无限膨胀。
4. **状态栏**：用 user 角色承载元信息（环境状态、任务进度、用户时间 / 工作状态），把隐式状态变显式。
5. **上下文压缩**：不是单纯截断，是主动总结把原始数据变高密度结构化知识（上下文感知压缩）。

## A2 · 何时用
- 上下文不断膨胀影响质量或超窗口。
- 需要让 Agent 感知环境 / 进度 / 用户状态。
- 提示词随功能增长难以维护。
- 区分：跨会话记忆 → 用 RAG / 双层记忆（ch3），非本方法。

## R · 证据
- ch2 整章：API 消息结构、KV Cache、提示工程、Skills、状态栏、压缩——共同点是显式工程化的知识管理。
- ch3：跨会话上下文管理（与 ch2 同属上下文支柱）。
- 思想根源：Sutton《苦涩的教训》——能更有效利用算力的通用方法胜出。

## A1 · 书中案例
- ch2 九个实验逐一覆盖 KV Cache 友好设计、提示工程、Skills、状态栏、上下文感知压缩。
- 状态栏语义注解：API 用 user 角色（无元信息角色），语义上是上下文五部分的补充注解。

## B · 不适用与边界
- KV Cache 友好性与布局灵活性冲突（频繁改前缀则缓存频繁失效）。
- 压缩有信息损失风险，需主动结构化总结而非简单截断。
- 兄弟 skill：推进循环用 react-loop；本方法解决「每步给模型看什么」。

# Agent 评估方法论详解

本文档详细展开 SKILL.md 中"方法论根基"章节提到的企业级 Agent 评估方法论。

**来源**：基于亚马逊云科技《企业生产级智能体开发部署指南》提炼。

---

## 3×3 评估矩阵全展开

### 支柱一：评估粒度（有多深）

| 粒度 | 定义 | 适用场景 | 示例 |
|------|------|----------|------|
| **黑盒** | 只看最终响应，不关注内部过程 | 面客问答 Agent、内容生成 Agent | 评估客服回答是否正确、营销文案是否吸引人 |
| **玻璃盒** | 看完整执行轨迹（工具调用链、推理步骤、中间错误） | 工具调用型 Agent、多步骤推理 Agent | 评估购物助手是否选对了 API、参数是否正确 |
| **白盒** | 逐步分析单步调用（每个工具调用、每个推理步骤） | 复杂工作流 Agent、多 Agent 协作 | 评估多 Agent 系统中每个子 Agent 的通信效率 |

**选择决策树**：
```
是否需要定位根因？
├── 否 → 黑盒
└── 是
    ├── 是否涉及工具调用 / 多步骤推理？
    │   ├── 是 → 玻璃盒
    │   └── 否 → 白盒
```

### 支柱二：证据权重（有多大分量）

| 证据层 | 定义 | 典型指标 | 打分器选择 |
|--------|------|----------|------------|
| **L1：机械可验证** | 能写成代码断言、规则检查 | 格式合规、JSON schema、枚举值校验 | 代码规则断言（deepeval） |
| **L2：半客观** | 有明确评分标准但需语义理解 | 正确性、完整性、一致性、工具选择准确性 | 校准过的 LLM-as-a-Judge |
| **L3：主观** | 依赖专家判断、难以明确标准 | 创意性、风格适配性、品牌语调 | 人工抽检 + 最终仲裁 |

**三类打分器对齐表**：

| 证据层 | 优先使用打分器 | 备选打分器 | 校准方法 |
|--------|----------------|------------|----------|
| L1 机械可验证 | 代码规则断言（deepeval） | — | 单元测试验证 |
| L2 半客观 | 校准过的 LLM-as-a-Judge | 人工抽检（验证一致率） | 专家写标准 → 对照人工标注验证一致率 ≥ 80% |
| L3 主观 | 人工抽检 | LLM 裁判（作为参考） | 专家组评审 |

**打分器选择决策树**：
```
该指标能否写成代码断言？
├── 是 → 使用代码规则（deepeval）
└── 否
    ├── 是否有明确的评分标准？
    │   ├── 是 → 使用 LLM-as-a-Judge（需校准）
    │   └── 否 → 使用人工抽检
```

### 八类测量维度（基于原文综合提炼）

文章提出"八类测量维度"，基于结语列举综合为以下八类：

| # | 维度 | 定义 | 适用场景 | 常见指标 |
|---|------|------|----------|----------|
| 1 | **最终答案正确性** | 输出事实是否正确、是否匹配用户意图 | 所有 Agent | Correctness |
| 2 | **中间推理质量** | 推理过程是否合理、逻辑是否严密 | 推理型 Agent | ReasoningSoundness, LogicalConsistency |
| 3 | **工具调用准确性** | 工具选择、参数是否正确 | 工具调用型 Agent | ToolCorrectness, ToolSelectionAccuracy, ParameterAccuracy |
| 4 | **责任合规性** | 是否遵守安全、法律、伦理约束 | 面客/专业领域 Agent | Safety, 合规性指标 |
| 5 | **延迟** | 响应时间是否在可接受范围 | 实时/高频交互 Agent | 延迟指标（秒级） |
| 6 | **成本** | Token 消耗、API 调用成本是否可控 | 大规模部署 Agent | 成本指标（Token 数/次） |
| 7 | **用户体验** | 输出是否友好、易理解、符合预期 | 面客 Agent | Coherence, 语气适配性 |
| 8 | **一致性（pass@k/pass^k）** | 多次运行的稳定性如何 | 关键业务 Agent | pass@k, pass^k |

**"按业务挑格子"示例**：

| Agent 类型 | 建议粒度 | 建议证据层 | 核心维度 |
|-----------|----------|------------|----------|
| **面客问答 Agent** | 黑盒 | L2（LLM 裁判） | 1, 7, 4, 8 |
| **内部工具调用 Agent** | 玻璃盒 | L1（代码规则）+ L2 | 3, 2, 5, 6 |
| **多 Agent 协作系统** | 白盒 | L2（LLM 裁判）+ L3（人工） | 2, 3, 8, 4 |
| **代码生成 Agent** | 黑盒/玻璃盒 | L1（代码可运行性）+ L2 | 1, 2, 5, 6 |

## 判定漏斗：expect → L1 → L2 → L3

借鉴 skill-up 的工程实践，每条 case 的判定按以下顺序逐层执行，**前置层失败即短路**，跳过后续更昂贵的判定，避免为明显失败的 case 浪费 LLM token。

### 执行顺序

| 层 | 名称 | 成本 | 判定内容 | 失败动作 |
|----|------|------|---------|---------|
| Step 1 | **expect 门槛** | 零（本地字符串/文件检查） | 冒烟门槛：关键词是否出现、文件是否存在、退出码是否为 0 | 直接 FAIL，跳过所有后续层 |
| Step 2 | **L1 机械可验证** | 低（代码规则） | 确定性检查：格式合规、JSON schema、枚举值、工具调用结构 | FAIL，跳过 L2 |
| Step 3 | **L2 半客观** | 高（LLM-as-a-Judge） | 语义评分：正确性、完整性、一致性等（仅对前两层通过的 case 执行） | 按分数判定 |
| Step 4 | **L3 主观** | 最高（人工） | 专家仲裁、创意性、品牌语调（抽检） | 人工判定 |

### expect 与 L1 的职责区分（关键，勿合并）

两者都属「确定性检查」，但职责不同：

- **expect** 是「这条 case 值不值得评判」的**冒烟门槛**。它不评质量好坏，只看是否触发了最低限度的预期信号（如输出里有没有出现「发布计划」三个字）。
- **L1** 是「格式/结构对不对」的**合规性检查**。它评估输出是否符合规定的结构（如 JSON schema、工具调用格式、枚举值范围）。

**举例**：一个 Agent 被要求生成发布计划。
- expect 判「输出里有没有出现『发布计划』『回滚』等关键词」——没有就说明答非所问，直接 FAIL，不必再评。
- L1 判「输出是不是合法的 Markdown 结构、时间格式对不对」——结构错了才 FAIL。
- L2 才判「这个发布计划写得全不全、合不合理」。

### 配置位置

expect 配置在评测用例的 `expect` 字段（详见 `references/dataset-schema.md`）。L1/L2/L3 的指标体系不变，仍按 `references/metric-catalog.md` 选择。

### 与多轮评测的关系

多轮对话场景中，expect 仍是 case 级的最终门槛；而**每轮之间**的过程门卫由 `post_condition` 承担（详见 `references/dataset-schema.md` 的多轮对话格式）。两者层级不同：expect 管整条 case 的冒烟，post_condition 管单轮的去留。

## 三类打分器详解

### 第一类：代码规则断言（L1 机械可验证）

**适用场景**：格式合规、JSON schema 验证、枚举值校验、工具调用序列确定性检查。

**工具**：deepeval 的 `JSONCorrectnessMetric`, `ToolCorrectnessMetric`, DAG 自定义指标。

**优势**：确定性高、可自动化、适合 CI/CD 门禁。

**局限**：无法评估语义质量（如"回答是否友好""推理是否合理"）。

### 第二类：校准过的 LLM-as-a-Judge（L2 半客观）

**适用场景**：正确性、完整性、一致性、工具选择准确性等需要语义理解的指标。

**校准方法**（关键）：
1. **专家写标准**：领域专家明确定义评分标准（参考 `references/metric-catalog.md` 的锚点示例）
2. **对照人工标注验证**：用 LLM 裁判对一批已有人工标注的 case 评分
3. **计算一致率**：LLM 裁判与人工标注的一致率应 ≥ 80%
4. **迭代调整**：如一致率不达标，调整评分标准或提示词，重新校准

**工具**：本 skill 生成的评估 Agent 提示词（`evaluator-prompt.md`）。

**优势**：能理解语义、上下文、意图；可规模化。

**局限**：需要校准；对模糊标准可能有噪声。

### 第三类：人工抽检与最终仲裁（L3 主观）

**适用场景**：创意性、风格适配性、品牌语调、多 Agent 协作的意外行为模式。

**操作方式**：
1. **抽检比例**：建议 5-10% 的评测 case 由人工复核
2. **争议仲裁**：当 LLM 裁判结果与人工预期不一致时，以人工为准
3. **标准更新**：从人工复核中发现的模式，更新 LLM 裁判的评分标准

**优势**：最权威、能处理复杂主观判断。

**局限**：成本高、无法规模化。

**HITL（Human-in-the-Loop）必选场景**：多 Agent 协作系统（可能产生设计者未预料的行为模式）、高风险业务（医疗、金融、法律）。

## 三层评估库（按对象分层定位根因）

当评测发现问题（如 pass@k 下降）时，需快速定位根因。三层评估库按评估对象分层：

| 层级 | 评估对象 | 问题示例 | 定位方法 |
|------|----------|----------|----------|
| **模型选型层** | 底层大模型 | 模型静默升级导致输出退化 | 周期性用同一评测集评估不同模型版本 |
| **组件层** | 意图、记忆、推理、工具 | 意图识别错导致路由错误 | 玻璃盒评估：分析每步执行轨迹，定位到具体组件 |
| **端到端层** | 整体业务结果 | 用户体验下降、投诉增加 | 黑盒评估：从最终答案入手，再逐层下钻 |

**根因定位路径**：
```
端到端评估发现问题
  ↓
黑盒评估（答案质量）
  ↓
玻璃盒评估（执行轨迹）
  ↓
定位到组件层（意图/记忆/推理/工具）
  ↓
若组件无误 → 检查模型选型层（模型升级？）
```

**与三层指标（L1/L2/L3）的区别**：
- 三层指标（L1/L2/L3）是**指标分类**（按指标类型：通用/能力/专属）
- 三层评估库是**评估对象分层**（按系统层级：模型/组件/端到端）
- 两者正交：可在任何评估对象层级使用任何指标类型

## 一致性评估操作（pass@k / pass^k）

### 定义

| 指标 | 定义 | 公式 | 适用场景 |
|------|------|------|----------|
| **pass@k** | k 次中至少 1 次成功的概率 | `pass@k = (成功次数 ≥ 1 的 case 数) / 总 case 数` | 一次成功就够的场景（推荐生成、创意任务） |
| **pass^k** | k 次全部成功的概率 | `pass^k = (k 次全成功的 case 数) / 总 case 数` | 一致性至关重要的场景（合规检查、安全审核） |

### k 取值建议

| 场景类型 | 建议 k 值 | 理由 |
|----------|-----------|------|
| 普通评测 | 3 | 平衡成本与可靠性 |
| 高可靠性需求 | 5 | 更严格捕捉非确定性 |
| 资源受限 | 1-2 | 降级方案，但需标注"单次评估" |

### 计算方式

对每个 case：
1. 跑 k 次被测 Agent（相同输入）
2. 每次用评估 Agent 评分（按 L1 指标，如 Correctness ≥ 4 算成功）
3. 统计 k 次中成功次数，计算 pass@k 和 pass^k

**示例**（k=3）：
- Case A：成功、失败、成功 → pass@3 = 1（至少1次成功），pass^3 = 0（非3次全成功）
- Case B：成功、成功、成功 → pass@3 = 1，pass^3 = 1
- Case C：失败、失败、失败 → pass@3 = 0，pass^3 = 0

### 与单次评估的关系

- **单次评估**：快速、成本低，但可能因非确定性而波动
- **k 次评估**：更可靠，但成本 ×k。建议：关键 case 做 k 次，一般 case 单次即可

详见 `references/evaluator-prompt-templates.md` 中的"模板 5: 一致性评估器"。

## 漂移管理操作指南

### 建立基线

首次评测后，保存为 baseline：

```json
{
  "baseline_id": "v1.0",
  "created_at": "2026-07-16",
  "agent_version": "v1.0",
  "evaluator_version": "v1.0",
  "summary": {
    "pass_at_3": 0.85,
    "pass_3": 0.72,
    "correctness_avg": 4.2,
    "safety_pass_rate": 1.0
  }
}
```

保存到 `{eval_workspace}/baseline/v1.0-eval-baseline.json`。

### 监控漂移

**周期**：建议每周或模型升级后重新评测一次。
**对比维度**：
- pass@k / pass^k 变化（如下降 > 10% 为警告）
- 单指标平均分变化（如 Correctness 从 4.2 降到 3.8）
- Safety FAIL 出现（从 0 到 ≥1 个 FAIL 为严重警告）

**漂移报告**：生成与上次基线的对比报告

```markdown
# 漂移检测报告

## 基线对比
| 指标 | 基线 v1.0 | 当前 v1.1 | 变化 |
|------|-----------|-----------|------|
| pass@3 | 0.85 | 0.78 | -0.07 ⚠️ |
| pass^3 | 0.72 | 0.65 | -0.07 ⚠️ |
| Correctness | 4.2 | 3.9 | -0.3 ⚠️ |
| Safety | 1.0 | 0.95 | -0.05 ⚠️ |

## 结论
模型升级后，评测指标出现 5-10% 的下降，建议回滚或调整提示词。
```

### 回归触发条件

设定告警阈值：
- **黄色警告**：pass@k 下降 5-10%，或单指标下降 0.3-0.5 分
- **红色告警**：pass@k 下降 > 10%，或 Safety 出现 FAIL，或 pass^k 下降 > 15%

**触发动作**：
- 黄色：告警通知，触发人工复审
- 红色：自动回滚到上一版本，或暂停上线

## 三个生产实例方法论提炼

### 实例 1：购物助手（工具使用评估）

**场景**：对接成百上千 API 和 Web 服务，schema 定义差会直接导致选错工具、推高延迟成本。

**方法论**：
1. **跨组织 schema 治理规范**：统一 API 描述格式（OpenAPI）、参数命名约定、错误码规范
2. **LLM 驱动的 API 自助接入**：数月流程压缩为自动流程（开发提交 schema → LLM 自动生成调用示例 → 自动回归测试 → 上线）
3. **基于历史调用日志的回归测试**：从生产日志中提取真实调用模式，构造评测集，确保新版本不破坏已有功能

**数据飞轮**：
- 生产日志 → 评测集（持续生长）
- 失败案例 → schema 治理规范更新
- 成功模式 → 自动化接入流程优化

### 实例 2：客服 Agent（意图检测评估）

**场景**：意图识别错会级联出路由错误与体验崩塌。

**方法论**：
1. **匿名化历史交互构造"用户查询+期望意图"真值对**：从生产日志中提取真实用户查询，人工标注期望意图，构造高信度评测集
2. **LLM 模拟器扮演虚拟客户批量生成长尾场景**：用 LLM 生成边缘、罕见场景的评测用例（如"我要退货但订单号丢了"），扩展评测集覆盖面

**数据飞轮**：
- 生产日志 → 真值对评测集
- 未见场景 → LLM 模拟器生成 → 补充评测集
- 错误模式 → 意图识别模型微调数据

### 实例 3：卖家助手（多 Agent 协作评估）

**场景**：Planner-Specialist 模式（一个规划 Agent + 多个专家 Agent），除个体指标外，还需评估协作效率。

**方法论**：
1. **个体指标**：每个 Agent 的正确性、工具调用准确性（沿用实例 1、2 的方法）
2. **规划得分**：评估规划 Agent 的任务分解合理性、资源分配效率
3. **通信效率**：评估 Agent 间消息传递的准确率、冗余度
4. **协作成功率**：评估端到端任务完成率（如"卖家上架商品"全流程）

**HITL 必选**：多 Agent 交互可能产生设计者未预料的行为模式，人工抽检是必选项，承担起 AI 指标难以替代的把关职责。

**协作指标示例**：
- 规划得分：5 分（任务分解清晰、资源分配合理）
- 通信效率：4 分（消息准确，偶有冗余）
- 协作成功率：0.85（85% 的端到端任务成功完成）

## 生产 Trace 回流为评测数据

### 数据格式建议

从生产日志中提取 Trace，转换为评测用例：

```json
{
  "id": "PROD-TRACE-001",
  "source": "production_log",
  "input": {
    "user_message": "我要退货，订单号 ORD-20250604-001",
    "timestamp": "2026-07-16T10:23:45Z"
  },
  "execution_trace": {
    "tool_calls": [
      {"tool": "get_order_info", "params": {"order_id": "ORD-20250604-001"}, "result": "success"},
      {"tool": "check_return_policy", "params": {}, "result": "7天无理由"}
    ],
    "reasoning_steps": ["用户意图是退货", "需先查询订单信息", "确认退货政策"],
    "errors": []
  },
  "actual_output": "您的订单 ORD-20250604-001 可以退货。根据7天无理由退货政策，您可以在订单签收后7天内申请退货。",
  "tags": ["退货", "真实生产"],
  "derived_evaluation": {
    "expected_intent": "退货咨询",
    "ground_truth_tools": ["get_order_info", "check_return_policy"],
    "quality_label": "good"
  }
}
```

### 回流策略

1. **采样频率**：建议每周采样 50-100 条生产 Trace
2. **标注方式**：人工标注 `derived_evaluation` 字段（期望意图、真值工具、质量标签）
3. **并入评测集**：将标注后的 Trace 转换为标准评测用例格式（见 `references/dataset-schema.md`），并入主评测集

### 用生产 Trace 评估的价值

- **真实性强**：覆盖真实用户意图、真实边缘场景
- **持续生长**：评测集随业务演进自动更新
- **复利回报**：Trace 可回流为评测数据 → 微调训练数据 → 模型能力提升

## 与 deepeval 的关系

- **本 skill（Prompt-based 评测）**：负责 L2 层（半客观）的语义质量评估（正确性、完整性、一致性等）
- **deepeval（代码化评测）**：负责 L1 层（机械可验证）的确定性检查（格式合规、JSON schema、工具调用序列）
- **互补关系**：两者可同时使用，各负责自己擅长的部分。详见 `references/deepeval-bridge.md`。

**三类打分器与 deepeval 的对应**：
- L1 机械可验证 → deepeval（代码规则）
- L2 半客观 → 本 skill（LLM 裁判）
- L3 主观 → 人工抽检

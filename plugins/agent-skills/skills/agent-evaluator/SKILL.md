# Agent Evaluator — Agent 评测 Harness 构建器

你是 Agent 评测专家。你的核心能力是用**自然语言提示词**构建完整的 Agent 评测体系，
而非编写测试代码。评测逻辑以 Prompt 形态存在，改文字就能改评测逻辑。

## 核心理念

- **Prompt-as-Code**: 评测标准、评分逻辑、判断规则全部以自然语言提示词定义
- **Agent 评测 Agent**: 一个评估 Agent 调用被测 Agent，对其输出评分
- **零部署**: 核心流程不需要安装额外 Python 包，纯 Prompt 驱动
- **快速迭代**: 修改提示词文本即可调整评测逻辑，无需改代码

## 方法论根基（为何传统评估对 Agent 失效）

Agent 与传统软件有三个本质差异，使评估从"测试环节"升格为"工程地基"：

1. **非确定性**：Agent 基于大模型，输出是概率性的，同样输入不一定产生相同输出。昨天通过的测试今天未必稳定。没有任何主流模型提供商承诺完全确定性的输出。

2. **改提示词 = 改代码**：修改系统提示词可能根本改变 Agent 行为，但不会留痕、无静态分析工具可预判影响。**每次提示词变更必须配套评估**。

3. **依赖会自己漂移**：模型是隐式依赖，提供商可能在后台静默升级，导致代码无变动但服务质量退化。**没有持续评估基线，漂移几乎不会被及时发现**。

**核心结论**：评估不是测试阶段的一次性活动，而是贯穿 Agent 全生命周期的持续工程纪律。建立评估体系 = 掌握 Agent 生命周期的核心。

### 3×3 评估矩阵（核心方法论）

企业评估 Agent 时，需要在两个维度上做出选择：

| | 支柱一：评估粒度（有多深） |
|---|---|
| **支柱二：证据权重（有多大分量）** | **黑盒**（只看最终响应） / **玻璃盒**（看完整执行轨迹） / **白盒**（看单步调用） |
| **L1：机械可验证** | 能写成代码断言的绝不交给评判模型 |
| **L2：半客观** | 校准过的 LLM-as-a-Judge，只管主观维度，标准由专家写并对照人工标注验证一致率 |
| **L3：主观** | 人工抽检和最终仲裁 |

这三类打分器与证据权重对齐：**第一层用代码规则 → 第二层用 LLM 裁判 → 第三层用人工**。详见 `references/evaluation-methodology.md`。

### 一致性指标：pass@k 与 pass^k

Agent 的非确定性要求 **k 次评估**：
- **pass@k**：k 次中至少 1 次成功的概率（适合一次成功就够的场景）
- **pass^k**：k 次全部成功的概率（适合一致性至关重要的场景）

详见 `references/metric-catalog.md` 中的"一致性指标"章节。

## 适用场景

- 评估自研 Agent 的输出质量（客服、编码、分析、创作等）
- 对比不同 Agent 或不同 Prompt 版本的表现差异
- 建立 Agent 上线前的质量门禁
- 为 Agent 构建回归评测集
- 生成结构化评测报告供团队评审

## 不适用场景

- 传统软件的单元测试/集成测试（用 tdd skill）
- 单次输出的主观感受（无结构化评估需求）
- 纯性能/延迟测试（需要工程化工具）

## 五阶段工作流

用户进入此 skill 后，按以下五阶段推进。每个阶段有明确的输入、输出和确认门禁。
用户可从任意阶段开始（比如已有评测集，直接从阶段 3 开始），但必须确认前置产出。

### 阶段 0: 定义与就绪检查 (Define)

**目标**: 明确"定义排在构建之前"，启动 Agent 评估前的四个必交付物。

**心智模型**: 盖楼前先出图纸。启动一个 Agent 评估项目，应产出以下四个具体交付物，才能进入阶段 1：

1. **能力边界的清晰定义**：这个 Agent 能做什么、不能做什么？输入边界是什么？输出边界是什么？
2. **语气与个性**：Agent 的角色设定（如"专业客服助手""亲和型咨询顾问"），语气风格（正式/口语化、简洁/详尽）
3. **工具与参数的精确描述**：每个工具的用途、每个参数的含义、可能的错误模式
4. **基准数据集（评估"燃料"）**：覆盖常见场景与边缘情况的初始评测数据集。没有数据集，评估无从谈起。

**三大就绪误区检查**（在进入阶段 1 前，确认避免以下坑）：
- ❌ 只关注 Agent 准确率指标 → ✅ 应覆盖多个维度（工具调用、推理、用户体验等）
- ❌ 用预期工具调用序列做精确匹配 → ✅ 应评估语义正确性，工具调用序列可容错
- ❌ 先评估后观测 → ✅ 先观测执行轨迹再决定评什么（玻璃盒/白盒评估）

**输出**: 四个交付物文档 + 基准数据集初版（可来自生产日志采样或 LLM 模拟器生成）。

**门禁**: 用户确认四个交付物齐备后，进入阶段 1。

---

### 阶段 1: 设计评测方案 (Design)

**目标**: 明确"评什么、怎么评、用哪些指标"。

**输入**: 用户对被测 Agent 的描述（prompt 文件、功能说明、业务上下文）、评测目的。

**过程**:

1. **明确被测对象**: 是哪个 Agent？输入是什么？输出是什么？调用方式是什么？
2. **确定评测范围**: 全能力评测 vs 专项评测（如仅评估工具调用准确性）
3. **选择指标层** — **在 3×3 矩阵上挑格子**：
   - 首先确定评估粒度（黑盒/玻璃盒/白盒）：只看最终答案？还是看执行轨迹？还是逐步分析？
   - 然后选择证据权重（L1 机械可验证 / L2 半客观 / L3 主观）：
     - **L1 通用基础指标**（必选，适用于所有 Agent）:
       - 正确性 (Correctness): 输出是否符合事实和用户意图
       - 完整性 (Completeness): 是否充分回应了用户需求
       - 一致性 (Coherence): 输出是否逻辑自洽、结构清晰
       - 安全性 (Safety): 是否包含有害、偏见或不当内容（一票否决）
     - **L2 能力类型指标**（按 Agent 类型选用，从 `references/metric-catalog.md` 选取）:
       - 工具调用型: ToolCorrectness, ToolSelectionAccuracy, ParameterAccuracy
       - 指令遵循型: InstructionAdherence, FormatCompliance, ConstraintFollowing
       - 推理型: ReasoningSoundness, LogicalConsistency, EvidenceGrounding
       - 创作型: Creativity, StyleConsistency, AudienceAppropriateness
       - 对话型: ContextMaintenance, TurnCoherence, PersonaConsistency
     - **L3 专属指标**（用户自定义，与用户一起设计）:
       - 领域特异性指标，如"医疗建议准确性"、"法律合规性"、"代码可运行性"
4. **确定评分机制与打分器选择** — **对齐证据权重**：
   - **L1 机械可验证层**：用代码规则断言，能写成代码的绝不交给评判模型（如格式合规、枚举值校验）
   - **L2 半客观层**：用经校准的 LLM-as-a-Judge（本 skill 的评估 Agent），只管主观维度，评分标准必须由领域专家写出来，并对照人工标注验证一致率
   - **L3 主观层**：人工抽检和最终仲裁
   - 评分方式：1-5 分 Likert 量表（默认推荐）、0/1 二值判定、百分制、自定义分级

**输出**: 一份 Evaluation Plan Document，格式如下:

```markdown
## Evaluation Plan

### 基本信息
- 被测 Agent 名称:
- Agent 类型: [工具调用/指令遵循/推理/创作/对话/混合]
- 评测目的:
- 评测范围:

### 指标体系
#### L1 通用指标
| 指标 | 权重 | 评分方式 | 说明 |
|------|------|----------|------|
| Correctness | 0.3 | 1-5 Likert | 事实正确性和意图匹配度 |
| Completeness | 0.25 | 1-5 Likert | 需求覆盖程度 |
| Coherence | 0.2 | 1-5 Likert | 逻辑自洽性和结构清晰度 |
| Safety | 0.15 | 0/1 二值 | 安全无害（一票否决项） |

#### L2 能力指标
| 指标 | 权重 | 评分方式 | 说明 |
|------|------|----------|------|

#### L3 专属指标
| 指标 | 权重 | 评分方式 | 说明 |
|------|------|----------|------|

### 评测约束
- 被测 Agent 调用方式:
- 每条评测用例超时:
- 评测用例数量:
- 评测集大小建议: 20-55 条（小而精）
```

**门禁**: 用户确认 Evaluation Plan 后，进入阶段 2。

### 阶段 2: 构建评测集 (Build Dataset)

**目标**: 创建结构化的评测用例集，每条用例包含输入、期望输出和元数据。

数据格式规范详见 `references/dataset-schema.md`。核心结构:

```json
{
  "meta": {
    "dataset_name": "agent-v1-eval",
    "version": "1.0",
    "agent_under_test": "被测 Agent 名称",
    "created_at": "2025-01-01",
    "description": "评测集描述",
    "metrics": ["correctness", "completeness", "coherence", "safety"]
  },
  "cases": [
    {
      "id": "EVAL-001",
      "category": "类别",
      "difficulty": "easy|medium|hard",
      "input": {
        "user_message": "用户输入",
        "context": {}
      },
      "expected_output": {
        "reference_answer": "参考答案",
        "key_points": ["关键点1", "关键点2"],
        "must_not_include": ["禁止内容"]
      },
      "tags": ["标签"],
      "notes": "备注说明"
    }
  ]
}
```

**构建策略**:

1. **从实际日志采样**: 优先从 Agent 真实对话日志中选取典型和边界 case
2. **按能力维度覆盖**: 确保每个 L2/L3 指标都有对应的测试用例
3. **难度分层**: 按 easy/medium/hard 分布，建议比例 5:3:2
4. **边界 case 设计**: 刻意设计异常输入、模糊请求、对抗性 prompt
5. **合成数据生成**（可选）: 基于指标体系让 LLM 批量生成评测用例

**最小可用**: 起步时 10-20 条用例即可。

**门禁**: 用户确认评测集后，进入阶段 3。

### 阶段 3: 编写评估 Agent 提示词 (Write Evaluator Prompt)

**目标**: 构建评估 Agent 的提示词——这是整个 Harness 的核心创新。

**先观测再评估**：在编写提示词前，先观测被测 Agent 的实际执行轨迹（工具调用链、推理步骤、中间错误），再决定评估重点。玻璃盒评估（看轨迹）比黑盒评估（只看结果）更能定位问题根因。详见 `references/evaluation-methodology.md` 中的"三层评估库"。

评估 Agent 的工作流:
```
读取评测用例 → 调用被测 Agent（或读取其输出）→ 按指标逐项评分 → 输出结构化 JSON
```

完整的提示词模板见 `references/evaluator-prompt-templates.md`。以下是核心结构:

```markdown
# Agent 评估器

你是一个专业的 Agent 输出质量评估器。

## 评估对象
- 被测 Agent: {agent_name}
- Agent 类型: {agent_type}

## 评测用例
**用户输入**: {user_input}
**上下文**: {context}
**被测 Agent 输出**: {agent_output}
**期望输出参考**: {expected_output}

## 评估指标

### L1 通用指标
{按 metric-catalog.md 中的评分标准填入}

### L2 能力指标
{按评测方案选用的指标填入}

### L3 专属指标
{按评测方案自定义的指标填入}

## 输出格式
严格输出以下 JSON:
{
  "case_id": "{case_id}",
  "scores": {
    "correctness": {"score": 0, "reasoning": "评分理由"},
    "completeness": {"score": 0, "reasoning": "评分理由"},
    ...
  },
  "overall_comment": "总体评价",
  "critical_issues": []
}
```

**关键原则**:
1. 每个指标都有**定义 + 评分标准**（锚点）
2. 每个分数必须附带 **reasoning**（可审计）
3. **结构化 JSON 输出**（便于自动聚合）
4. L2/L3 指标可**插拔**（根据评测方案动态拼入）
5. 多轮对话用例：**过程门卫（post_condition）与最终裁判（评估器）分工**——post_condition 在每轮后由执行框架检查（早停），评估器只做整场最终评判，不重复 post_condition 已检查的断言。详见 `references/evaluator-prompt-templates.md` 模板 4 与 `references/dataset-schema.md` 多轮对话格式

**门禁**: 用户确认评估提示词后，进入阶段 4。

### 阶段 4: 跑批评测 (Run Batch)

**目标**: 对评测集中每条用例执行评估，收集评分结果。

**执行方式**（按推荐优先级）:

#### 方式 A: 纯 Prompt 驱动（零部署，默认推荐）

**判定漏斗执行顺序**（借鉴 skill-up，前置层失败即短路，省 token。详见 `references/evaluation-methodology.md`「判定漏斗」）：

1. **调用被测 Agent**：将用例 input 送入被测 Agent 获取 actual_output（离线评测则直接读取已有输出）
2. **expect 门槛**：对 actual_output 跑零成本本地断言（`must_contain` / `must_not_contain` / `exit_code` / `files_exist`）。失败 → 直接记为 FAIL（`raw/case-{id}.json` 标 `failed_at: expect`），**跳过 L2 LLM 评判**
3. **L1 代码规则**：格式/schema/工具调用结构检查。失败 → FAIL，跳过 L2
4. **L2 评估 Agent 评分**：将通过前两层的 actual_output 连同评估提示词交给评估 Agent（subagent）执行语义评分
5. **收集结果**：所有评分 JSON 保存到 `{output_dir}/raw/case-{id}.json`
6. **L3 人工抽检**：按需对争议 case 复核

> 核心收益：明显失败的 case 在 expect/L1 阶段就被拦截，不会消耗昂贵的 LLM 评判 token。

批量执行建议:
- 使用 subagent 并行评估，每批 5-10 条
- 保留每条原始评估 JSON 以备审计

#### 一致性评估：pass@k 与 pass^k（应对非确定性）

由于 Agent 输出的非确定性，单次评估可能不稳定。对关键 case 进行 k 次评估（k 建议 3-5 次）：

- **pass@k 执行**：对同一 case 跑 k 次，只要至少 1 次通过即算 pass。适合一次成功就够的场景（如推荐生成、创意任务）。
- **pass^k 执行**：对同一 case 跑 k 次，要求 k 次全部通过才算 pass。适合一致性至关重要的场景（如合规检查、安全审核）。

详见 `references/evaluator-prompt-templates.md` 中的"一致性评估器"模板和 `references/metric-catalog.md` 中的"一致性指标"章节。

#### 方式 B: deepeval 集成（需要 Python 环境）

当用户需要工程化评测（CI/CD、确定性检查、合成数据）时，使用 deepeval。
详见 `references/deepeval-bridge.md`。

## 持续评估与漂移管理

评测不是一次性活动，而应贯穿 Agent 全生命周期。

### ADLC 六环飞轮（评估驱动生命周期）

与传统线性软件开发（需求→设计→开发→测试→上线）不同，Agent 开发应是首尾相连的闭环飞轮：

```
定标准 → 开发实现 → 效果评估 → 灰度上线 → 持续监控 → 改进循环 → 回到定标准
```

**核心要点**：
- **"生产"不是终点**，而是飞轮最富价值的输入
- 每个生产中暴露的真实失败案例，都比会议室里预设的测试用例更有价值
- 评估集应随生产数据持续生长
- **生产 Trace 回流**：生产环境中的执行轨迹（工具调用链、推理步骤、错误模式）应回流为评测数据，进而可成为微调训练数据，形成复利回报

详见 `references/evaluation-methodology.md` 中的"漂移管理操作指南"和"生产 Trace 回流数据格式"。

### 漂移管理与评估基线

**建立基线**：首次评测后保存为 baseline（评分快照），后续评测与 baseline 对比，及时发现退化。
**监控漂移**：定期（建议每周或模型升级后）用同一评测集重新评估，对比基线指标变化。
**触发阈值**：设定回归触发条件（如 pass@k 下降超过 10%、Safety 出现 FAIL），触发告警和回滚决策。

**输出目录结构补充**：
```
{eval_workspace}/
├── baseline/                  # 持续评估基线（每次评测后保存快照）
│   ├── v1.0-eval-baseline.json
│   └── drift-report.md        # 与上次基线的对比报告
├── plan.md
├── dataset.json
├── evaluator-prompt.md
├── raw/
├── scores.csv
└── report.md
```

## 快速通道

对于想快速出结果的场景（用户说"快速评测"或"简单看看"）:

1. **精简方案**: 仅使用 L1 四个通用指标 + 1 个最相关的 L2 指标
2. **精简评测集**: 5-10 条核心用例，无需 expected_output
3. **精简提示词**: 使用 `references/evaluator-prompt-templates.md` 中的 Quick Eval 模板
4. **内联执行**: 直接在当前会话中评估，不启动 subagent
5. **精简报告**: 仅输出总体评分和 Top 3 优劣势

## NEVER

NEVER 在没有确认评测方案的情况下直接开始评测。即使是快速评测，也要确认评测维度。

NEVER 编造评测结果。每条评分必须有评估 Agent 的原始 JSON 输出作为依据。

NEVER 用关键词匹配代替语义评估。"Agent 评测 Agent"的核心价值在于评估 Agent 能理解
语义、上下文和意图，而非简单字符串比对。

NEVER 忽略安全性指标。安全性不通过时，必须在报告中醒目标注。

NEVER 在一次评测中使用过多的 L3 自定义指标（建议不超过 3 个）。指标越多，评估提示词
越长，评估一致性越差。先聚焦核心指标，验证稳定后再扩展。

NEVER 将此 skill 用于非 Agent 场景（如搜索引擎排序、推荐系统）。

NEVER 只盯准确率指标。应覆盖工具调用、推理、用户体验等多个维度（见阶段 0 的"三大就绪误区"）。

NEVER 对工具调用序列做精确匹配。应评估语义正确性，允许工具调用序列容错（如调用顺序差异、冗余调用）。

NEVER 先评估后观测。应先观测执行轨迹（玻璃盒/白盒），再决定评估重点（见阶段 3 的"先观测再评估"）。

## 边缘情况

### 被测 Agent 无法程序化调用
降级为"离线评测"模式: 用户提供被测 Agent 的历史输出（对话日志、文本文件），
评估 Agent 直接对这些已有输出评分。评测集中需填入 `actual_output`。

### 评测结果一致性差
同一 case 多次评估分数差异大时:
1. 检查评估提示词是否足够具体（评分标准是否有清晰锚点）
2. 对争议 case 进行"人工校准": 人与评估 Agent 同时打分，对齐标准
3. 考虑将 Likert 量表降为三级（好/中/差）以降低噪声

### 用户只想评测单条输出
允许单条评测。跳过阶段 2，直接用评估提示词模板对单条输出评分。输出简版评分结果。

### 用户要求对比两个 Agent
在评测集中增加 `variant` 字段（如 "agent-v1" vs "agent-v2"），对同一批输入分别评测，
在报告阶段增加 A/B 对比分析板块。

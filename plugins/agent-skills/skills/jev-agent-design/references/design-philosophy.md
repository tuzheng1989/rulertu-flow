# Jev Agent 的设计哲学

这是对一组社区实现的**归纳和工程建议**，不是证明了适用于所有 Jev 工作负载的定律。证据以各项目 README 为主，具体来源与核验程度见 [社区案例](community-patterns.md)。案例来自 [awesome-jev-hub](https://github.com/supermanc417-alt/awesome-jev-hub) 及其链接的 [v-modal/awesome-jev-tools](https://github.com/v-modal/awesome-jev-tools)、[Anil-matcha/awesome-jev-by-typesafe](https://github.com/Anil-matcha/awesome-jev-by-typesafe)、[heyjunpenn/awesome-jev](https://github.com/heyjunpenn/awesome-jev) 等清单。清单彼此转载或共享项目，不能按出现次数推断独立验证，也不能从项目宣传推断生产表现。

## 设计判断

### 1. 先设计决策接口，再决定是否用模型

先列系统要作出的动作、授权和可观察结果，再倒推哪些输入确实需要语义判断。把问题拆成独立、具体的判断，让代码用明确的规则组合输出；精确查表、权限、数值运算和硬约束留给代码。Jev 适合填补规则难以表达、但输入和输出边界清晰的语义判断。参考：[TypeSafe 官方指南](https://github.com/typesafe-ai/skills/blob/main/skills/typesafe-ai/SKILL.md)、[Canny](https://github.com/qkal/Canny)、[SystemOneHarness](https://github.com/HarnessRouter/SystemOneHarness)。

**反例与边界**：简单正则已经稳定识别且有明确规则时，增加 Jev 可能只是增加延迟和故障点；开放式写作、规划或缺少可枚举候选的问题可能仍需生成模型或人。是否划算要与现状实测。

### 2. 构造判断环境：好状态、好候选比模型名称更基础

输入应让判断者看见当前目标、相关事实和可选项；候选由系统筛选、命名并约束合法性，和当前环境绑定。浏览器元素索引只对某次观察有效；技能短名单缺失正确答案时，选择器无法把它找回来。[jev-ultrafast](https://github.com/browser-use/jev-ultrafast) 的动态动作表与指纹检查、[技能路由器](https://github.com/GodsBoy/jev-agent-skill-router) 的分批收缩和弃权，体现了不同场景的候选工程。

**推论**：状态投影过短会丢证据，过长会提高成本并引入无关或对抗性内容；候选裁剪要单独测召回，最终 shortlist 内的 Choice 概率是条件分布，不能视作全库正确概率。把输入投影、候选构造与题目版本一起评估。

### 3. 多层协作，把判断放在流程真正需要的位置

Jev 可以用于调用前选择、调用中动作或调用后核验；自由生成交给 LLM，动作由宿主执行。同一系统可把「是否值得唤醒」「是否有证据回答」「输出是否有支撑」分成不同判断，而不是将一个总分复用于所有阶段。[wakegate](https://github.com/shitianfang/wakegate) 在唤醒前筛选事件；[Cribrix](https://github.com/david96182/cribrix) 在生成前筛上下文、生成后审查断言；[Reflex](https://github.com/kaustav1996/reflex) 在行动、路由和完成检查中使用不同问题。

**反例与边界**：同模型前后两次判断可能共享偏差，并不构成统计独立验证；高频多层调用还可能累积误拒绝和网络开销。验证应结合执行结果、确定性检查或独立证据，而不是只看另一模型分数。

### 4. 不确定性是控制流的一部分，不是一个置信度数字

设计明确的执行、弃权、升级和不可用分支。对封闭选项，最高分只意味着相对更优，候选都不合适时需有 `none` 或独立适配判断。区分模型判断的概率、接口失败和缺失证据；按场景和错误代价校准门槛。参考：[技能路由器](https://github.com/GodsBoy/jev-agent-skill-router)、[Cribrix](https://github.com/david96182/cribrix)、[pi-verdict](https://github.com/jesset/pi-verdict)。

**反例与边界**：增加固定高阈值可能把正常工作大量送审，也不能抵御所有攻击；[jev-engineering](https://github.com/eugeniughelbur/jev-engineering) 自报告的注入实验中，冒充授权仍有漏检，阈值调高伴随正常流量升级。项目数据只反映其有限测试集，不能外推为通用攻击率。

### 5. 失败方向由错误后果决定

同样是门控，两个决策的默认动作可以相反。wakegate 服务失败时唤醒，是为了避免遗漏待处理事件；用户消息和跳过次数上限等也有强制唤醒。pi-verdict 在无法判定时阻止或询问，是为了避免未经授权的动作；非交互场景的询问退化为拒绝。jev-engineering 则让自身判断失败退回宿主原有权限流程，而不是宣称无条件允许。

**设计时逐项写清**：误放行、误阻断、漏唤醒各有什么后果？超时/缺键/解析失败走哪条已有路径？人工不可达时怎么办？高影响动作的安全性依靠权限系统和隔离，模型建议不能覆盖宿主硬约束。Jev 在安全中的使用不是防注入证明。

### 6. 系统优化目标是闭环效用，而非单次调用速度

观察从请求、候选、决策、动作到结果的完整链路，支持离线回放与按版本定位问题。成批判断可共享状态，但多轮筛选仍有网络、重复状态、并发与失败成本；缓存还需覆盖状态、题目、模型和策略变化。比较任务成功率、错误代价、人工介入、端到端延迟与总费用。参考：[jev-codex-router 回测](https://github.com/0xNatoshi/jev-codex-router/blob/main/BACKTEST.md)、[技能路由器评测](https://github.com/GodsBoy/jev-agent-skill-router)、[Cribrix 评测](https://github.com/david96182/cribrix)。

**反例与边界**：技能路由器公开的 72 条合成请求用于迭代过问题，不能视为独立泛化基准；Cribrix 自述的 62 条样本也有宽置信区间，且其基线检索窗口不同。复用思路时按目标任务重新冻结样本、基线、模型版本和阈值。

### 7. 按时间尺度分层，状态决定能否判断

在需要持续控制或实时响应的系统里，感知、安全反射、执行控制和语义判断可以各自运行；速度快慢及职责应由真实系统的时限决定。Jev 的建议有使用时限，不能让网络延迟拖住关键控制；高频确定性控制与独立的安全约束应能在模型异常时持续工作。参考：[jev-drone 仿真](https://github.com/RomanSlack/jev-drone)、[驾驶仿真](https://github.com/kavehmz/typesafe-playground)。

先检查判断所需信息是否可观察：无人机仅有水平距离时无法判断障碍是否可越过，增加可见性、障碍顶边高度和爬升限制后才具备判断依据。领域专家的知识因此体现在观测字段、单位与未知值、候选动作和验收样本中。**边界**：字段齐全只是必要条件，不保证判断正确；仿真频率和单次成功不构成真实硬件安全证据。详细的时间与状态契约见 [具身与实时决策](embodied-systems.md)。

## 如何套用：一张决策卡

对每个候选接入点写下：

| 项 | 需要明确的内容 |
| --- | --- |
| 后果 | 当前决策及可观测结果；误放行与误拒绝的不同代价 |
| 状态与候选 | 由谁生成、过滤和保鲜；正确答案不在候选时如何处理 |
| 判断与策略 | 题目及类型；模型结果如何与确定性规则组合 |
| 权限与退路 | 谁执行；低信心、冲突、服务异常、人工不可达时分别做什么 |
| 时效 | 在变化环境中，观察与建议何时过期；延迟、超时和控制周期怎样衔接 |
| 证据 | 哪些反馈能证明结果；日志/缓存怎样绑定模型、题目、状态与策略版本 |
| 验证 | 原系统基线、代表性正反例、对抗/故障样本、成功率、成本和 p95 延迟 |

**示例：长期监控 Agent。** 输入是等待目标、事件摘要和可廉价获取的新观察；Jev 判断事件与等待目标的关系，代码对用户消息、定时检查和连续跳过上限执行既定规则；缺键或超时保留原唤醒路径。影子运行先记录本来会被跳过的事件，人工抽样核查漏掉重要事件的比例，再比较实际省下的生成调用与端到端延迟。这里的规则是适配方案，具体实现以 wakegate 原项目为准。

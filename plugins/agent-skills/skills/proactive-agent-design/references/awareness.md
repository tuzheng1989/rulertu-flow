# Awareness：察觉

【原文】维护跨请求可用的情境估计。论文 §4.1、图 7 包含四部分：多模态状态跟踪与上下文、主动感知与信息获取、分层记忆，以及可在没有新查询时运行的触发／监控／休眠计算架构。交接材料的三子能力需补入第四项运行时架构。

【导读】问答记忆有查询作为相关性锚；值守感知需要用受托职责界定何种变化相关。因此与 Agenda 联合设计：每个监控都能回答「它服务哪条职责，改变什么决策」。监控拓扑本身是设计对象。

需要做出的决策：

- 哪些信源更新哪些状态；数据的来源、观察时间、有效期与冲突如何保留。
- 事件订阅、定期轮询和按需查询分别适用哪里；无新消息时由什么唤醒。频率取决于变化速度、决策期限与成本预算。
- 缺一条信息是否会改变选择；值得补证时自动检索、等待信源还是询问用户。把计算、能源、隐私和注意力成本一起考虑。
- 跨会话怎样保存、更新、失效与重查；旧事实过期后不能继续当作确定状态。

【实现约定】最小感知记录可含 `signal_source / observed_at / valid_until / mandate_ref / state_delta / evidence_ref / uncertainty`，按任务裁剪。输出是带证据的当前情境估计及信息缺口。

**诊断与验证**：

- 看不见变化：先查信源覆盖、触发器和运行时是否实际运行。
- 看见一切却找不到相关工作：查职责锚与筛选，而非只加更多记忆。
- 陈旧事实持续驱动待办：查有效期、冲突处理与重新获取。
- 用同一份原始变更材料，在没有新任务指令的条件下验证能否更新情境；另给无关变化，检查监控成本与噪声。

**环间接口**：向 Anticipation 提供事实与不确定性，接收其假设查询；Agenda 反向限定相关范围，Adaptation 用执行结果修正失效的状态。

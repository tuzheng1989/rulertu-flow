# Action：行动

【原文】在获准范围内落实介入，并保留人的有效控制。论文 §4.5、图 11 将行动选择、呈现形态和编辑／撤销／接管／失败恢复连在一起；可审核的提案与已经生效的变更有不同错误成本。

需要做出的决策：

- 明列系统支持的形态：建议、询问、提醒、草稿、预览、授权执行；哪些可编辑、取消、回滚、中途人工接管，能力覆盖到什么阶段。
- 呈现改动、成本归因和生效状态。用户应看清改了什么、费用或资源从哪里产生、哪些仍待审批或尚未提交。无金钱交易时写相关资源成本或不适用。
- 以实际工具回执和外部状态判定是否生效；超时不等于失败，更不等于可安全重试。
- 跨应用没有整体原子性时逐段记录成功、失败、结果未知；说明重查、重试、补偿与人工接管路径。

【导读】部分失败需要独立状态机并回写 Agenda。可撤回性工程越好，Arbitration 的选择空间越大；不能先承诺高介入，再假定执行工具一定能撤销。

【实现约定】按需要区分 `prepared / awaiting_approval / committed / failed / unknown / compensated`。确认前后若证据、价格或范围改变，回到 Arbitration。重启时先核对已提交段，避免重复外部副作用。

| 场景 | 应保留的状态与恢复信息 |
|---|---|
| 草稿完成、未获许可 | 草稿位置、差异、有效期，明确尚未生效 |
| A 应用成功、B 应用失败 | 两段回执、外部状态、可补偿范围与下一步，整体记部分完成 |
| 请求超时、结果不明 | 结果未知、查询／去重依据；核对后再决定是否重试 |
| 用户接管 | 已完成与未完成段、当前外部状态、可继续或停止的位置 |

【导读】差异呈现还能在真实取舍点采集偏好，但采集要受用户模型的归因纪律约束；一次编辑不自动定义长期偏好。

**失败与验证**：方案不可审、草稿被误报为已执行、部分失败被掩盖、重试重复提交。模拟一段成功一段失败或超时，验证外部状态核对、逐段进度和恢复呈现。

**环间接口**：向 Arbitration 提供真实能力与错误成本；向 Agenda 回写逐段进度；向 Adaptation 分开提供执行结果和用户对呈现／方案的反馈。

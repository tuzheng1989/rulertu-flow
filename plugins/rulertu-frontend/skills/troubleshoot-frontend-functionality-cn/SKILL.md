# 前端问题排查与修复

先证明故障在哪一层，再改代码。回退值和假数据很容易让错误从界面上消失，但错还留在系统里。

## 先判断任务证据边界

- 用户只要方案，给的请求/响应字段、报错或复现链路又够定位时，直接拿这些证据诊断；不要去搜本机、容器或无关的示例仓库，也不要为了显得有过程再去读补充资料。
- 用户要求修改代码且提供了仓库时，先读仓库约定和最小范围的相关文件，再做只读复现；没有仓库就给出能落地的假设方案、最小补丁位置和回归测试，不把运行环境里的 Agent SDK 或依赖目录当成业务仓库。
- 用户说的事实和仓库证据对不上时，把冲突列出来，以能复现的证据为准；确认不了的内容标成待验证，不伪造文件名、调用栈或运行结果。

核心诊断不靠 `references/` 也能做完。只有当前问题确实涉及缓存键、请求竞态、旧闭包或乐观更新，而且光看主文档定不了实现时，才按已挂载 Skill 的实际目录读取 `references/failure-patterns.md`；路径确认不了或读取失败，就立即回到下面的主流程，不猜测文件路径、不反复重试。

## 建立可复现的故障现场

固定页面、账户、权限、设备、版本和操作步骤，记录预期、实际、控制台、请求响应和状态快照。从接口原始响应开始，顺着适配层、缓存、状态容器、组件属性追到页面元素，找到最早对不上的位置。

把脱敏后的接口响应和界面实际读取的字段保存为 JSON 后，运行 `python3 scripts/compare_contract.py response.json expected-fields.json`，先查有没有缺字段、路径错位和类型变化。脚本只能给契约层面的证据，替代不了运行时状态、权限和事件检查。

脚本不可用时，手工逐路径核对原始 JSON、适配器输入输出和组件读取字段，保留同样的缺失/类型差异表；不得让排障卡在装工具上。

接口返回成功不代表数据正确；把字段、类型、空值、分页、时区、错误体和权限过滤都查一遍。排查点击问题时，检查点击热区、禁用条件、事件绑定、冒泡、路由和异步竞态。

症状涉及富文本、跳转、身份或敏感字段时，一并检查不可信 HTML、开放重定向、鉴权/CSRF 沿用和控制台泄露；没有相关证据，就不要把安全检查扩成全站审计。

断网、超时与主动取消必须分开：记录浏览器错误、HTTP 状态、超时预算和请求是否被新操作取消；不得把所有失败归为“网络异常”后自动无限重试。先弄清数据归谁管：React Query 缓存、Vue/Pinia store、组件本地状态，还是内部框架封装；再在数据归属的那一层修复，不要为了套用示例而迁移状态库。

## 定位链路上最早出错的一层

沿“响应 → 适配 → 缓存 → 全局状态 → 组件属性 → 事件 → DOM”这条链，拿正常样本和异常样本逐层对比。在每一层记录“输入事实、期望、实际、最小反证”；第一次出现差异的层就是当前修复边界，后续空态或错误文案只是症状。字段错配时必须同时保留原始响应路径和消费路径，例如 `data.items` 与 `data.rows`，说清默认空数组、可选链或回退值是怎么把契约错误伪装成正常空态的。

涉及请求竞态、缓存键、旧闭包、字段回退或乐观更新时，选和当前项目的状态库、请求库、数据所有者一致的模式；不得把示例库名称或实体照搬进仓库。需要补代码模式时再读 `references/failure-patterns.md`，别把读参考文件当成必经步骤。

先写能复现原始症状的测试或稳定复现脚本。每次只验证一个根因；接口、状态、样式一起改，改完就分不清是哪项起了作用。修数据源或契约本身，不要靠加默认值把必填数据的缺失盖过去。

涉及缓存和并发时明确数据所有者、失效条件、请求取消和晚到响应策略。涉及乐观更新时，写清失败怎么回滚、重复提交怎么处理。发现是后端契约的错，给出证据，在正确的那一层修。

## 用原始报障场景验收

用原账户和原步骤证明问题消失，运行修复前失败的回归测试，再检查加载、空、失败、权限、刷新和快速连续操作。最后写清楚：最早出错的环节、根因的机制、代码改了什么，以及反证过的候选原因。

只要求方案时，至少交付：最早出错的环节、证据链、唯一修复层、边界之外哪些不改，以及一个修复前必失败且修复后通过的回归测试。测试要断言用户可见的结果或适配器契约，不能只断言请求被调用过。最终答复禁止出现 Skill 文件、挂载路径、内部工具尝试、路径猜测或“我来读取”等执行过程。

# 网页性能优化

没有同口径基线就没有性能优化。先证明用户受影响，再决定改资源、代码、数据还是架构。

## 建立可复测基线

固定页面、构建版本、设备、浏览器、网络、缓存和登录状态。每轮测量结果存成 JSON，运行 `python3 scripts/compare_metrics.py baseline.json candidate.json` 算出变化量，确认候选值是否算术上进入预算。实验室指标拿来复现问题，真实用户数据拿来判断覆盖面；两者不能混成一个数字。记录样本数、中位数和高分位，不能只挑最好的一次结果。

任何“通过预算”或“性能改善”的结论必须在同一段明确写出可比前提：同页面、同构建、同设备档位、同浏览器、同网络、同缓存、同登录态和同分位。即使用户已经给出“同一页面、冷缓存、p75”，也要在结论里把其余还没确认的口径复述一遍；没有确认就写“数值在预算内，发布结论待同口径复测”，不能写“可以合并”“已稳定达标”或无条件宣布通过。

复测分成两道闸门，不能混用：第一道，在页面、构建、设备、浏览器、网络、缓存、登录态、样本数和分位都与基线完全相同的条件下重复采集，用来判断改动收益；第二道，等第一道通过后再扩展到低端设备、弱网和其他真实用户分布，用来判断收益是否普遍成立。换设备或换网络的结果不能反过来证明前后改动有效。用户只给了聚合值、没给样本数和波动时，准确结论是“这组数值均在预算内，但稳定性未证实”。

报告中的指标表必须逐行复制脚本输出的 `metric/before/after/budget/within_budget`，保留原单位；不得凭上下文手抄多个候选值。手工计算时每行先写“指标名 + 单位”，再代入基线值和候选值，并逐行复核，避免把 LCP 的毫秒值写进 JS KB 那一行。

脚本不可用时，按同一公式手工算前后差值，留一份口径表；测量工具不可用、环境不一致或样本不足时，只交付测量方案并说明当前限制，不声称已经优化。症状复现不了，先核对真实用户的页面、设备、网络和版本分布，再挑一个有代表性的受控环境。

按用户症状选指标：首屏慢看最大内容绘制和关键资源，交互响应慢看交互延迟和主线程长任务，布局跳动看布局偏移，列表卡顿看帧率与渲染次数，内存增长看堆快照与监听器。

## 优化被证实的瓶颈

用网络瀑布图、性能 trace、包体积分析和组件分析弄清时间花在哪一段：连接、服务端、资源下载、解析执行、渲染还是第三方脚本。第三方请求按域名、资源类型、阻塞阶段和主线程任务分别统计，不能只写“第三方较慢”。国内用户路径还要检查 DNS、TLS、跨境或跨运营商链路、实际 CDN 节点，以及备案域名下的资源到底能不能访问到；未经团队批准，不得把“换公共 CDN”当作默认修复方案。

先确认页面是 SSR/SSG/CSR 还是混合渲染：服务端响应慢、客户端水合慢和纯 CSR 首屏空白的瓶颈不同，基线必须记录渲染模式与对应构建版本。需要判断资源加载、主线程、框架渲染、列表或内存问题时，读取[性能故障模式](references/performance-patterns.md)，只用和证据对得上的模式。先修关键路径上贡献最大的那项，不要因为“最佳实践”就去动不在关键路径上的代码。

代码示例用 React 只是演示一种控制方式；Vue、原生页面或其他框架就用项目里已有的延迟计算、取消、虚拟化和资源加载机制，不要为了套示例换技术栈。

## 确认收益没有把成本转移到别处

每次变更只对应一个主要假设，记录指标、样本、波动与副作用。在同一环境下复测，并分别列出两类回归：低端设备/弱网/缓存命中的性能回归，以及登录、提交、路由、错误恢复等关键用户功能回归；两者不能互相替代。检查无障碍性；验证过确实有效的阈值，加进性能预算或持续监控。最终报告第一句直接写“通过、暂通过、未通过或不可比较”及其条件；接着给基线、变更后数据、置信度与局限、实现代价和回退方式，别在表格后面再把结论拔高。测量细则见[网页性能诊断方法](references/method.md)。

# 网页界面开发

交付的是能正常用的界面，不是只在某一个截图尺寸下看着像的静态画面。

## 先适配当前项目

先运行 `python3 scripts/inspect_frontend.py <项目根目录>`。从输出确认框架、包管理器、路由、状态/请求库、测试工具、样式方案和可用命令；再读它定位到的配置文件和两个相邻页面。不得把 React、Vue、Tailwind 或任一组件库当默认答案。

脚本不能运行时，手动读取最近的 `package.json`、锁文件、框架/构建配置、路由入口和相邻页面，标清楚哪些还没识别出来；不要为了探测项目去装依赖，也不要因为脚本跑不了就停下实现。

用户已明确框架、请求库或现有惯例，但没有提供仓库时，不得只回复“先探测项目”。用户已经定下的技术选择，就当事实用；文件位置、封装名称和设计令牌标成待替换的假设，然后照常给出组件边界、数据适配、状态模型、关键代码和测试。拿到仓库后，只替换这些假设，按真实命令验证，不另起一套架构。

材料只有截图时，先分清哪些是看得见的事实、哪些行为还不知道。截图能确认层级、文案、相对布局和当前状态，不能证明点击逻辑、权限、接口、异常、跨屏和动效。先按可替换的假设做一版实现，把必须确认的点写在对应交互旁边，别到结尾才用一段免责声明统一带过。

## 把界面做成状态机

先列 `状态 × 事件 × 下一状态 × 可见反馈`，再写组件。页面至少要处理首次加载、成功、空、失败、无权限、部分数据和重复提交；表单要写清校验时机、字段错误、提交中、服务端失败和成功后状态。接口字段只在适配层转换，不让服务端字段名扩散到所有组件。

需要 React/Vue 的接口适配、异步状态、表单与响应式实现时，读取 [框架实现模式](references/framework-patterns.md)，只用和仓库技术栈对得上的段落。示例里的 `Project`、`fetchProjects` 等名称必须换成当前仓库的真实实体，禁止把占位代码原样交出去。

## 落到真实行为上验收

响应式布局按内容断点设计，检查窄屏操作、触控目标、键盘焦点和滚动。不能用模拟数据、硬编码用户名、空数组回退或默认成功，把接口没接通的事实盖过去。复用现有模式；新抽象至少要有第二个真实使用点，否则先留在功能内部。

把服务端文案、富文本和 URL 当作不可信输入；默认靠框架转义，真要渲染 HTML 时用项目已有的白名单清洗。沿用现有鉴权与 CSRF 机制，不把令牌和非必要的个人信息写进日志、测试夹具和浏览器存储。

运行项目已有的格式化、类型检查、测试和构建命令。在目标浏览器走通主流程，检查控制台、失败请求、焦点、溢出、返回/刷新后的状态。最后说清楚：改了哪些用户可见的行为、用什么命令验证的、还有哪些真实约束没确认。完整检查见[网页界面交付检查](references/method.md)。

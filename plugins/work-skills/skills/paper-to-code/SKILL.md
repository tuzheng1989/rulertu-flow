# Paper-to-Code: 论文代码复现工作流

将学术论文系统性地复现为可运行的代码框架。核心理念：**只复现论文中描述足够详细的部分，明确标记信息缺口，不做无依据的猜测。**

## When to use

- 用户提供论文 PDF 路径、arXiv 链接，要求代码复现
- 用户问"这篇论文能复现吗"、"帮我实现这篇论文的方法"
- 用户想从论文中提取架构设计并实现代码
- 用户要求评估某篇论文的复现可行性

## Phase 1: 论文解析

### 1.1 提取文本

用 Python + PyMuPDF 提取 PDF 文本。分批读取，避免上下文溢出：

```
import fitz, sys
sys.stdout.reconfigure(encoding='utf-8')
doc = fitz.open('<pdf_path>')
for i in range(start, end):
    text = doc[i].get_text()
    print(f'=== PAGE {i+1} ===')
    print(text[:3000])
```

注意 Windows 下 `sys.stdout.reconfigure(encoding='utf-8')` 避免 GBK 编码错误。

### 1.2 分段精读

按以下顺序阅读，每步提取关键信息：

| 阅读顺序 | 关注内容 | 提取什么 |
|---------|---------|---------|
| Title + Abstract | 论文核心主张 | 一句话总结、核心方法名称 |
| Introduction | 问题定义、方法动机 | 解决什么问题、与现有方法的差异 |
| Method/Architecture | 系统架构、算法设计 | 模块划分、数据流、关键数据结构 |
| Experiments | 实验设置、结果 | 评估基准、超参数、对比方法 |
| Appendix | 实现细节 | 伪代码、文件结构、参数表、schema |

### 1.3 提取实现关键信息

重点关注论文中以下"高价值"内容：

- **架构图**：系统有哪些模块、模块间的数据流
- **伪代码/算法描述**：可以直接翻译为代码的逻辑
- **超参数表**：具体数值，对应配置文件
- **文件结构描述**：目录布局，对应项目骨架
- **Schema/接口定义**：数据格式，对应数据模型
- **公式**：数学计算逻辑

这些信息决定了复现的可行性——描述越具体，复现越可靠。

## Phase 2: 可行性评估

从三个维度评估，给用户一个清晰的结论：

### 维度一：架构描述清晰度

- 论文是否给出了完整的模块划分？
- 模块间的数据流是否清晰？
- 是否有架构图或流程图？

### 维度二：核心信息完整度

逐项检查：

| 检查项 | 高价值 | 中价值 | 缺失 |
|-------|--------|--------|------|
| 算法伪代码 | 可直接翻译 | 描述可推断 | 完全未提 |
| 数据结构/Schema | 精确定义 | 部分描述 | 需猜测 |
| 超参数具体值 | 全部列出 | 部分列出 | 未提 |
| Prompt/模板 | 完整提供 | 示例片段 | 完全未提 |
| 文件结构 | 详细附录 | 简要提及 | 未提 |

### 维度三：依赖可获得性

- 需要的模型/API 是否公开可用？
- 评估基准（benchmark）是否公开？
- 对照组实现是否可获取？
- 特殊硬件/环境需求？

### 输出格式

给用户一个结构化的评估报告：

```
## 复现可行性评估

### 可以复现的部分（~X%）
- 模块 A：论文有完整描述
- 模块 B：附录提供了 schema
...

### 难以复现的部分（关键瓶颈）
- 核心组件 X：prompt 模板未公开
- 评估基准 Y：不确定是否公开
...

### 结论
[可以复现框架 / 可以部分复现 / 不可复现]
建议的复现范围：[框架骨架 / 完整系统 / 仅算法核心]
```

**等用户确认复现范围后再继续。** 这是关键决策点，不要跳过。

## Phase 3: 框架设计

### 3.1 模块映射

将论文章节映射到代码模块。每行注明对应论文的位置：

```markdown
| 代码模块 | 对应论文 | 实现内容 |
|---------|---------|---------|
| module_a.py | Section 3.2 + Appendix B | 数据模型 + 解析器 |
| module_b.py | Section 3.3 | 核心算法 |
| ...
```

### 3.2 目录结构设计

基于论文描述的架构设计项目结构。如果论文有文件结构描述（通常在附录），优先遵循。

### 3.3 确定实现顺序

按依赖关系排序，从底层到上层：

```
1. 数据模型（无依赖）→ 验证：解析/序列化 round-trip
2. 核心逻辑（依赖数据模型）→ 验证：单元测试
3. 编排层（依赖核心逻辑）→ 验证：集成测试
4. CLI/入口（依赖全部）→ 验证：端到端运行
```

### 3.4 声明假设

明确列出实现中需要猜测/推断的部分：

```
假设：
- 论文未提供 X 的具体实现，我采用 Y 方案（理由：...）
- 超参数 Z 论文未提及，默认值为 ...（理由：...）
```

## Phase 4: 分步实现

### 4.1 核心原则

- **Simplicity First**：每个模块只实现论文描述的功能，不添加"灵活性"或"可配置性"
- **Surgical Changes**：遇到 bug 只修复 bug，不顺带"改进"其他代码
- **Test Per Module**：每个模块完成后立即写测试并验证通过，再进入下一个

### 4.2 实现节奏

每个模块的标准流程：

```
1. 写源码（~50-150 行为佳，超过 200 行考虑拆分）
2. 写测试（覆盖正常路径 + 边界情况）
3. 运行测试
4. 如果失败：修复 → 重跑 → 确认通过
5. 标记完成，进入下一个模块
```

### 4.3 测试策略

| 测试类型 | 何时写 | 测什么 |
|---------|--------|--------|
| Round-trip | 数据模型 | 解析 → 序列化 → 再解析，数据一致 |
| CRUD | 存储层 | 创建、读取、更新、删除 |
| 状态转换 | 状态机 | 合法转换通过，非法转换拒绝 |
| 集成 | 模块组合 | 端到端流程（创建→评估→注册→使用） |

### 4.4 遇到论文信息不足时

- **停止并说明**：告诉用户"论文未提供 X 的具体实现细节"
- **提供选项**：列出 2-3 种合理的替代方案，让用户选择
- **不要猜测**：宁可留接口空位，也不要填入无依据的实现

## Phase 5: 文档生成

### 5.1 方法总结文档

为复现的代码创建一份方法总结文档，包含：

- **一句话描述**：这个系统做什么
- **定位**：在更大系统中的角色（与相关工具的关系）
- **核心设计**：每个关键模块的设计思路
- **源码映射表**：文档中的每个概念对应哪个源文件
- **与论文的对应**：每个模块对应论文的哪个 section/appendix
- **未复现部分**：诚实列出论文中有但代码未实现的部分

### 5.2 更新项目 README

更新项目的 README，反映新增模块的结构和文档入口。

## 关键原则总结

1. **论文是合约**：只实现论文中明确描述的部分，不做超范围扩展
2. **映射可追溯**：每个代码模块都能追溯到论文的某个 section/appendix
3. **信息缺口透明**：明确标记哪些是论文未提供的、需要假设的部分
4. **分步验证**：每个模块独立测试，不攒到最后一起验证
5. **骨架优先**：先复现数据结构和流程骨架，再填充算法细节
6. **区分复现层次**：框架骨架（结构对等）≠ 完整系统（行为对等）≠ 实验复现（数值对等）

# 工作总结

将工作记录按目标和成果汇总为易读的总结。先确定读者、时间范围、数据源和输出要求；用户给定的口径优先。未指定时按本地日历理解日、月、季度、半年和年度；周报沿用上周一 12:00 至本周一 12:00 的既有口径。使用当前系统时间确定相对日期，明确展示实际起止时间和时区。采集窗口采用左闭右开 `[起点, 终点)`，展示日期时避免把不含的终点写成涵盖的一天。未完成的当前周期标明截至时间。

## 采集和判断

用户提供的材料优先；需要本地记录时，可运行 `scripts/collect.py` 采集 Claude Code、Codex 历史和指定根目录下直接子目录中的 Git 仓库。脚本默认周窗口及仓库根 `D:/runspace`；只在数据源与任务相关且可访问时使用。Hermes 可用时通过 session_search 补充；不可用或缺失的来源须注明，不能据此认定没有工作。

```bash
python {baseDir}/scripts/collect.py --start 2026-01-01 --end 2026-02-01 --summarize -o data.json
python {baseDir}/scripts/collect.py --days 7 --repos D:/work -o data.json
```

`--start` 和 `--end` 接受本地 ISO 日期或日期时间，终点不含；`--days` 是截至现在的 N 个 24 小时。`--summarize` 从完整会话抽取首段、成果候选和里程碑，能减少上下文，但它不是经过验证的总结：首段未必是复述，最长尾段未必是成果，完整会话还可能跨越窗口。对重要结论、日期和状态回查原始会话或其他证据，不能把窗口外成果算入本期。Git 记录按作者时间筛选，默认包含各作者；个人贡献须结合证据判断。Codex 项目归属可查 rollout 的 `session_meta.cwd`；工作台项目 `evoCenter` 按会话拆分，文档工作保留文档名。同一项目的不同目录名称需辨认后合并。

对于月度及更长周期、或资料无法舒适放入上下文时，读取 [分尺度融合](references/multiscale.md)，按子窗口逐层处理；不要直接把全部采集 JSON 一次放入上下文。短周期也可在资料量大时使用该流程。

## 成稿

按目标合并跨会话、跨来源的同一工作，保留成果、状态、关键指标及必要背景；区分已完成、进行中、失败与计划，不把模型陈述或提交标题直接当作交付事实。保留能支撑判断的证据，缺失或冲突时标明不确定性；避免重复累计跨周期工作或无依据的数字。忽略无实质内容的记录。

用读者能理解的语言解释内部代号和自造缩写，保留有意义的数字与通用术语。结构随周期和读者调整：概览、按项目或主题的主要进展、问题与后续计划通常足够；长期总结应突出阶段变化、累计成果与未解决事项。计划只取有依据的遗留或明确计划，缺少时说明待定。默认每项目保留最重要的几项，用户要求详细程度优先。

将总结写到用户指定目录，未指定时写到当前目录；默认文件名为 `YYYY-MM-DD - 工作总结.md`（周期终点日期），聊天中附文件路径。不要自动发送给他人。

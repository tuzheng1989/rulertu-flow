# 工作总结

将工作记录按目标和成果汇总为易读的总结。先确定读者、时间范围、数据源和输出要求；用户给定的口径优先。未指定时按本地日历理解日、月、季度、半年和年度；周报沿用上周一 12:00 至本周一 12:00 的既有口径。使用当前系统时间确定相对日期，明确展示实际起止时间和时区。采集窗口采用左闭右开 `[起点, 终点)`，展示日期时避免把不含的终点写成涵盖的一天。未完成的当前周期标明截至时间。

## 工作区与模式

1. 确定个人或团队模式、读者、目标、结构、周期和主要来源；用户提供的要求和资料优先。团队模式每次请用户指定成员总结目录，读取 [团队融合](references/team.md)。
2. 运行 `python {baseDir}/scripts/workspace.py get` 读取用户级全局工作区配置。首次无配置时请用户指定工作区，然后运行 `set <目录>`；目录须已存在且可读写，脚本保存规范化绝对路径。配置不可读、目录不存在或不可访问时说明问题，请用户指定可用目录，不静默切换。只有用户明确要求更换默认工作区时运行 `set`；本次输出目录只影响本次输出。受环境权限限制无法保存配置时说明并请求必要授权。
3. 月度及更长周期运行 `discover <工作区>` 发现 Markdown 和纯文本候选，按 [分尺度融合](references/multiscale.md) 核查；发现列表不代表可信或完整。旧总结无元数据时须读取内容判断，不能仅凭文件名认定周期或归属。
4. 输出目录为本次指定目录，否则为工作区。运行 `reserve <输出目录> <周期终点日期> <personal|team>` 原子创建不覆盖的文件，再写入该文件；失败须报告，不换目录。个人和团队文件名区分模式。聊天中附路径，不自动发送给他人。

新总结在 Markdown 开头记录以下 YAML frontmatter（ISO 8601 时间含时区偏移；终点不含），同时在正文说明实际覆盖、主要来源和影响结论的缺口。`subject` 是个人身份或团队名称；不明时写 `unknown`，不得猜测。来源记录可回查的位置或明确说明不可回查。

```yaml
---
work_summary: 1
mode: personal
subject: "姓名或团队名"
start: "2026-01-01T00:00:00+08:00"
end: "2026-02-01T00:00:00+08:00"
timezone: "Asia/Shanghai"
sources: ["来源路径或标识"]
---
```

## 采集和判断

用户提供的材料优先；需要本地记录时，可运行 `scripts/collect.py` 采集 Claude Code、Codex、ZCode 历史和指定根目录下直接子目录中的 Git 仓库。脚本默认周窗口及仓库根 `D:/runspace`；只在数据源与任务相关且可访问时使用。Hermes 可用时通过 session_search 补充；不可用或缺失的来源须注明，不能据此认定没有工作。

```bash
python {baseDir}/scripts/collect.py --start 2026-01-01 --end 2026-02-01 --summarize -o data.json
python {baseDir}/scripts/collect.py --days 7 --repos D:/work -o data.json
```

总结前需要拉取最新代码时，运行 `scripts/pull_repos.py` 批量拉取自研仓库。脚本从 `D:/runspace/evoCenter/研发项目简介.md` 的分级章节读自研清单（特级/一级/二级/三级；参考仓库与纯本地仓不拉），单仓独立超时、失败自动重试、代理/直连双通道、24h 缓存跳过已最新仓库；只拉不推（ff-only 合并，分叉显式报错）。结果 JSON 含 updated/unchanged/local_ahead/diverged/failed 分类，失败仓库须如实注明而非略过。

```bash
python {baseDir}/scripts/pull_repos.py --json pull_result.json   # --force 强制全量，--timeout 40 单仓超时
```

需要检查重点仓推送状态时（如每日推送守护定时任务），运行 `scripts/push_watchdog.py`：检查 FOCUS_REPOS（复用 pull_repos.py 的重点关注清单）是否有「已提交但未推送」，有则自动推送——默认→代理→直连双通道重试，push 被拒不自动合并、只报告；未提交的工作区更改不感知不处理。stdout 只在有推送动作或异常时输出 ✅/❌/⚠️ 报告，全部干净时 stdout 为空、退出码 0；过程日志走 stderr，判定只看 stdout。调用方约定：stdout 为空即全部干净，静默结束不投递；非空时将 stdout 原文（保留换行）转交指定接收人；退出码 1 表示存在推送失败或检查异常，须如实注明而非略过。

```bash
python {baseDir}/scripts/push_watchdog.py            # stdout 人类可读报告（干净时为空）
python {baseDir}/scripts/push_watchdog.py --json out.json   # 结果另存 JSON
```

`--start` 和 `--end` 接受本地 ISO 日期或日期时间，终点不含；`--days` 是截至现在的 N 个 24 小时。`--summarize` 从完整会话抽取首段、成果候选和里程碑，能减少上下文，但它不是经过验证的总结：首段未必是复述，最长尾段未必是成果，完整会话还可能跨越窗口。对重要结论、日期和状态回查原始会话或其他证据，不能把窗口外成果算入本期。窗口内只发生入库、归档动作的成果（上期完成、本期落仓），按入库或归档动作表述，不重复叙述成果内容。Git 记录按作者时间筛选，默认包含各作者；个人贡献须结合证据判断。Codex 项目归属可查 rollout 的 `session_meta.cwd`；ZCode 项目归属取会话首个 `Primary working directory`，取不到归入 `zcode` 组。工作台项目 `evoCenter` 按会话拆分，文档工作保留文档名。跨仓工作的章节归属按业务归属判断，不由物理仓库决定：工作台或文档仓中服务于某项目的工作（立项材料、档案更新、配套实验、项目目录调整）并入对应项目章节，该仓章节只保留自身事务。同一项目的不同目录名称需辨认后合并。

对于月度及更长周期、或资料无法舒适放入上下文时，读取 [分尺度融合](references/multiscale.md)，按子窗口逐层处理；不要直接把全部采集 JSON 一次放入上下文。短周期也可在资料量大时使用该流程。

## 成稿

按目标合并跨会话、跨来源的同一工作，保留成果、状态、关键指标及必要背景；区分已完成、进行中、失败与计划，不把模型陈述或提交标题直接当作交付事实。保留能支撑判断的证据，缺失或冲突时标明不确定性；避免重复累计跨周期工作或无依据的数字。忽略无实质内容的记录。

用读者能理解的语言解释内部代号和自造缩写，保留有意义的数字与通用术语。结构随周期和读者调整：概览、按项目或主题的主要进展、问题与后续计划通常足够；长期总结应突出阶段变化、累计成果与未解决事项。章节型总结（周报、月报）在每节开头给一句综述，让读者只读各节综述即可掌握全期里程碑：只列该节里程碑式节点，不含过程细节；一句一断，句号分隔。综述用平实动词（完成、上线、跑通、选定），不用渲染式表述；组件称呼优先用业务功能名，必要时括注正文别名，保证综述可脱离正文独立阅读。选哪些里程碑由当期用户反馈校准。计划只取有依据的遗留或明确计划，缺少时说明待定。默认每项目保留最重要的几项，用户要求详细程度优先。

按工作区与模式中的规则保存总结。

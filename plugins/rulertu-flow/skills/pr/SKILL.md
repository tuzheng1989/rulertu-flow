# PR 写作

让熟悉项目、但没有参与这次开发的维护者，读完就能理解为什么改、改后有什么变化、哪些证据支持合并，以及哪些实际限制会影响判断。

默认用中文叙述，保留代码标识符与必要的英文术语。用户的明确要求优先，其次遵循目标仓库的规范与适用 PR 模板。没有强制模板时，篇幅与结构随改动复杂度调整。

## 触发与提醒

- 会话内创建或更新 PR（`gh pr create`、`gh pr edit` 或向网页粘贴文案）前，标题与正文先经本技能依据最终 diff 起草；插件附带的 PreToolUse 守卫会在未经起草时向模型提醒一次。
- 完成其他任务后用户准备发 PR 时，主动提示可用本技能（或 `/pr`）起草；用户明确要求跳过时不再坚持。

## 明确比较范围与事实依据

读取相关仓库规范、适用 PR 模板、需求或 Issue，以及目标范围的实际 diff；必要时查看相关代码、提交记录和现有验证结果。

- 用户已指定 base/head 或现有 PR 时，沿用该范围。否则从本地分支信息中核实目标分支；有多个合理目标且差异影响主旨时询问，不直接假定为 `main`。
- 对分支 PR，查看 `git diff <base>...<head>` 等价的合并基点到 head 的累计变化。提交记录帮助理解背景，正文围绕最终 diff 组织。
- 未提交改动仅在用户要求提前准备草稿且明确包含它们时纳入；在可复制的文案之外说明草稿范围。
- 改写已有 PR 时，重新核对当前最终改动，更新标题和正文中的范围、行为与验证结论。
- 只有用户提供的补丁或描述时，可据此起草并说明依据的局限。背景动机不明时，写已知变化；缺失信息影响主旨或合并判断时再询问。

区分三类信息：从改动能确认的事实、需求中明确的目的、实际验证能证明的结果。性能、可靠性或兼容性结论需要对应证据，不能仅从“新增了测试”推导出“测试通过”。

## 先写问题和结果

标题概括这次 PR 的核心变化，让维护者仅看标题也能识别目的。标题格式遵循仓库约定；没有要求时，用一句具体的中文描述，不强制加 commit type 前缀。

正文开头交代具体问题或需求，以及修改后会发生什么。适合时用一个触发条件和前后行为说明，不要求读者先看 Issue、提交记录或讨论历史。

- 新功能说明谁在什么场景下获得什么能力；修复说明触发条件与修复后的行为。
- 文档、测试、构建或重构说明实际产物、流程或结构的变化，以及已核实的原因；不虚构面向用户的效果。
- 关键技术细节用于解释行为、边界或取舍，术语与项目保持一致。多个并列变化可用短列表，但按意图组织，不把文件清单或 commit log 当成正文。
- 最终采用的设计需要解释时，写它解决的约束和实际代价；开发经过、试错和已放弃方案只在能帮助评审当前取舍时保留。

“优化候选检索，提升质量”信息不足。若事实与证据支持，可以写：“候选中包含失效资源时，原先先截取再过滤，会少返回结果。这次改为先过滤再截取，让有效资源能够补足候选数量。”

## 按复杂度补充合并依据

简单 PR 使用一两段加验证说明即可。复杂 PR 按需要增加“改动”“设计取舍”“验证”“风险与迁移”等小标题；仅保留有实际内容的部分。仓库强制模板中的必填项按要求填写，不适用时据实说明。

验证说明要让维护者知道检查了什么、结果如何、还有什么实际缺口：

- 使用可核实的检查名称或命令和结果，必要时补充覆盖场景。记录测试通过数量时核对实际输出。
- 将通过、失败、未运行和范围不足分开表述；失败或相关未覆盖路径影响合并判断时，说明影响。已有证据可以复用，写文案本身不要求重跑测试。
- CI 尚未完成时写待完成，不能预报为通过；不把定向检查描述为全量验证。
- 有实际兼容性变化、部署前提或迁移步骤时，交代受影响对象、行动要求与已知限制；不为凑栏目添加泛化风险，也不在缺少依据时宣称“无风险”。

下面是短 PR 的写法示例。**仅在证据确实支持时使用其中事实**，示例测试路径与结果不能当作真实执行记录：

```markdown
标题：修复失效资源导致候选数量不足的问题

候选中包含失效资源时，原先先截取再过滤，会少返回结果。
这次改为先过滤再截取，让有效资源能够补足候选数量。

验证：`python -m pytest tests/test_candidates.py -q` 通过，
覆盖失效资源混入候选和有效资源不足两种情况。
```

## 交付与检查

分别输出可直接复制的标题和 Markdown 正文，将必要的范围假设、待确认事项放在复制区域之外。默认提供一个完整稿，只有用户要求或存在实质取舍时提供多个版本。

交付前核对：只读标题与开头能否理解目的及行为变化；描述是否覆盖当前最终 diff；验证是否有证据且范围准确；取舍和迁移信息是否足够支持合并判断；能否删掉重复、空泛或与评审无关的内容。

本技能只负责文案。实际 push、创建或更新 PR 等操作沿用会话中已有授权；调用写作技能本身不增加操作授权，也不要求重复确认已有授权。

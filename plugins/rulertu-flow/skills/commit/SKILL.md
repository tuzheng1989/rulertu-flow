# Commit 写作

让熟悉项目、但没有参与这次开发的维护者，在浏览历史时看懂这次提交改变了什么，以及值得保留的原因和约束。

默认用中文叙述，保留代码标识符与必要的英文术语。用户的明确要求优先，其次遵循目标仓库的明确规范；没有格式要求时使用下方默认格式。历史提交可用于了解惯例，但不自动成为硬性要求。

## 触发与提醒

- 会话内执行任何 `git commit`（含已授权的自动提交）前，message 先经本技能依据实际改动起草；插件附带的 PreToolUse 守卫会在未经起草时向模型提醒一次。
- 完成其他任务产生待提交改动时，主动提示可用本技能（或 `/commit`）起草；用户明确要求跳过时不再坚持。
- 改写已有提交说明（`--amend`、变基交互）同样适用。

## 先确定这次提交包含什么

读取目标仓库的相关规范、`git status --short` 和实际 diff，必要时查看相关代码与需求上下文。

- 用户指定提交或改动范围时，以该范围为准；改写已有提交说明时，读取该提交的 diff。
- 未指定范围时，优先依据 `git diff --cached`，将未暂存和未跟踪的内容留在本次说明之外。
- 没有暂存内容时，可以依据工作区改动起草，并在可复制的文案之外标明“基于未暂存改动的草稿”。未跟踪文件按用户选定的范围读取。
- diff 不可访问时，可依据用户提供的补丁或事实写草稿，说明依据的局限。范围有歧义且会改变标题主旨时，先澄清。

从改动中提炼一个主旨。涉及多个无关目的时，指出范围混杂，按用户指定的整体范围概括或提供分组文案建议；写作任务本身不拆分提交或改动暂存区。

## 标题：具体对象与变化

默认格式为 `type(scope): 中文标题`，scope 仅在有助于定位时使用。

- type 随改动目的选择，例如 `feat`、`fix`、`refactor`、`docs`、`test`、`chore`；scope 使用项目内可识别的模块名。
- 标题直接写具体变化或结果，让读者在 `git log` 中就能区分这次提交。长度保持便于扫描，不为固定字数牺牲含义。
- 将“优化逻辑”“提升稳定性”等泛称换成具体动作与场景。文件名、函数名只有在能帮助识别变化时才进入标题。
- 文档、测试或内部重构，说明实际产物或结构怎样变化；仅有这些改动时，不推导出未经验证的产品效果。

例如，假设 diff 确认调整了过滤与截取顺序：

较弱：`fix: 优化检索逻辑`

更清楚：`fix(retrieval): 过滤失效资源后再截取候选集`

## 正文：只补标题容纳不下的上下文

标题已足够解释简单改动时，只输出标题。需要保留原因、约束、兼容性影响或关键取舍时，空一行后补充短段落。

- 原因说明具体触发场景及原有问题，变化说明修改后的行为。保留理解这次选择所必需的边界条件。
- 按含义组织叙述；文件清单、函数清单和开发过程通常不能解释原因，无需逐项转述 diff。
- 每个关键结论都应能追溯到 diff、相关代码、需求说明或已获得的验证证据。动机不明时，省略无依据的因果解释；缺失信息影响主旨时询问用户。
- 兼容性破坏和迁移要求确实存在时写清楚，并遵循仓库的 breaking change 与 footer 约定。Issue 编号沿用已核实的关联。
- 验证仅在帮助理解改动或仓库要求时写入正文，准确区分实际通过、失败、未运行及覆盖范围；写作本身不要求重跑测试。

假设还已核实“原先先截取再过滤，失效资源会占用候选名额”，正文可写为：

```text
fix(retrieval): 过滤失效资源后再截取候选集

原先先截取再过滤，候选中存在失效资源时会少返回结果。
调整处理顺序，让有效资源能够补足候选数量。
```

这是长度和信息选择的示例，不要求每次套用相同句式。

## 交付与检查

输出一个可直接复制的完整 message，使用文本代码块。只在存在影响判断的假设、范围歧义或用户要求比较时，另附简短说明或备选稿。

交付前核对：标题是否概括了实际提交范围；必要的原因与约束是否有依据；去掉文件清单后，维护者是否仍能理解这次变化；是否存在重复、空泛的效果宣称或未经核实的验证结果。

本技能只负责文案。实际暂存、commit、amend、push 等操作沿用会话中已有授权；调用写作技能本身不增加操作授权，也不要求重复确认已有授权。

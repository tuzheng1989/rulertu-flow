# 深化模块

本参考说明如何在已知依赖的情况下，安全地把一组浅模块深化。术语以 [codebase-design.md](codebase-design.md) 为准。

## 依赖分类

评估深化候选对象时，先分类其依赖。类别决定深化后的模块如何跨 seam 测试。

### 1. 进程内依赖

纯计算、内存状态、无 I/O。始终可以深化：合并模块，直接通过新接口测试，不需要适配器。

### 2. 可本地替换依赖

存在本地测试替代品的依赖，例如用 PGLite 替代 Postgres、使用内存文件系统。存在可靠替代品时可以深化；测试套件运行该替代品。seam 留在内部，不要把端口暴露到模块外部接口。

### 3. 远程但自有的依赖：端口与适配器

跨网络调用的自有服务，例如微服务或内部 API。在 seam 上定义**端口**，由深模块拥有业务逻辑，并把传输实现作为**适配器**注入。测试使用内存适配器，生产使用 HTTP、gRPC 或队列适配器。

建议表述：在 seam 上定义端口，生产使用 HTTP 适配器，测试使用内存适配器；即使跨网络部署，逻辑仍集中在一个深模块中。

### 4. 真正的外部依赖

无法控制的第三方服务，例如 Stripe、Twilio。深化后的模块通过注入端口接收外部依赖，测试提供 mock 适配器。

## 接缝纪律

- 一个适配器只是设想中的 seam，两个适配器才形成真实 seam。至少存在生产与测试两种合理适配器时才引入端口；单适配器 seam 只是额外间接层。
- 深模块可以有实现私有的内部 seam，也可以在接口处有外部 seam。不要因为测试使用内部 seam 就把它暴露到公共接口。

## 测试策略：替换，不叠加

- 深模块接口测试建立后，原浅模块的单元测试通常已经失去价值，应删除而不是继续叠加。
- 新测试写在深模块接口上；接口就是测试表面。
- 只通过接口断言可观察结果，不断言内部状态。
- 测试应能承受内部重构。如果实现变化就必须修改测试，说明测试越过了接口。

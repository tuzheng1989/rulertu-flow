# 设计两次

当任务需要为选定的深化候选探索不同接口时，使用并行设计模式。第一版想法通常不是最优解，因此至少设计两次。术语以 [codebase-design.md](codebase-design.md) 为准。

## 流程

### 1. 界定问题空间

派发设计任务前，先向用户说明：

- 新接口必须满足的约束；
- 依赖及其分类，分类方法见 [deepening.md](deepening.md)；
- 一段用于具体化约束的粗略代码草图。草图不是方案，只用于建立共同语境。

说明后立即进入下一步，让用户阅读思考的同时并行开展设计。

### 2. 并行产生不同设计

在运行环境允许委派时，并行派出至少三个独立设计任务，每个任务必须产生**显著不同**的深模块接口。分别提供技术简报：文件路径、耦合关系、依赖类别、seam 后面的内容，并赋予不同设计约束：

- 方案一：最小化接口，最多保留 1–3 个入口，最大化每个入口的杠杆；
- 方案二：最大化灵活性，支持更多用例和扩展；
- 方案三：围绕最常见调用方优化，让默认路径尽可能简单；
- 方案四（适用时）：围绕端口与适配器处理跨 seam 依赖。

简报同时包含本参考词汇和项目 `CONTEXT.md` 中的领域词汇，确保架构语言与领域语言一致。

每个设计输出：

1. 接口，包括类型、方法、参数、不变量、顺序和错误模式；
2. 调用方使用示例；
3. seam 后隐藏的实现；
4. 依赖与适配器策略；
5. 权衡：哪里杠杆高，哪里仍然较薄。

若运行环境不支持并行委派，则由主控在相互独立的约束下依次产出多个候选，不能只给一个方案。

### 3. 展示、比较并推荐

依次展示候选设计，再用文字比较其深度、局部性和 seam 位置。最后给出明确推荐及理由；如果不同设计的部分组合后更强，可以提出混合方案。用户需要的是有立场的判断，不是无倾向的菜单。

# 专利撰写：发明专利技术交底书

为已确认的专利项起草技术交底书，供专利代理人撰写申请文件。交底书的读者是代理人：要的是**完整、清楚、可复现的技术方案**，不是宣传文案。技术方案直接决定权利要求边界，写得含糊就是白送保护范围。

## 输入

1. **专利项**：来自 `patent-analysis` 的候选清单（用户已确认）或用户直接指定。至少要有：技术问题、区别特征、代码证据。缺这三样的先退回分析或向用户补问。
2. **模板路径**：用户指定交底书模板 `.docx`。用户没给时问；不要用网传模板替代。
3. **撰写人信息**：姓名、电话、邮箱、内部编号——只有用户提供才填，留空比编造好。

## 工作流

1. **复制模板。** 把模板复制到输出目录，只操作副本，原模板不动。用 `python-docx` 读取副本，定位各章节标题段（按标题文本匹配，不硬编码段落索引——模板可能改版）。
2. **清理示例。** 模板中的示例内容（编写建议、缺省文本、例句）全部删除或替换，不残留上一个项目的任何字句。样式跟随模板原有样式，不新造样式。
3. **逐章起草。** 按模板章节结构（各模板大同小异，以实际模板为准）：

   - **术语解释**：全文英文缩写在此给中文译名和英文原词；正文首次出现处再标注一次。
   - **技术问题**：一句话讲清要解决的技术问题，必须是技术问题（速度慢、成本高、误码率高、不可靠），不是市场痛点。
   - **技术背景 + 最接近现有方案**：公知技术铺垫 + 最接近的现有实现（方法写步骤、装置写结构组成）。按 `patent-analysis` 清单中推定的最接近现有技术起草，标注这是申请人认知、待代理人检索确认。
   - **缺点推导与发明目的**：用因果链从现有方案推导缺点（因为 X 所以导致 Y 所以 Z），缺点只写本发明能解决的；目的与缺点一一对应。
   - **技术方案详述**（核心，至少 2 页）：总体架构 → 关键流程逐步展开 → 每个功能点的实现方案。从代码证据起草：算法步骤与代码逻辑一致，参数、数据流、模块边界取自仓库事实；用户口述的设计要点补充「为什么这样设计」。方法专利必须给流程图，并配系统/装置描述。
   - **关键点与欲保护点**：从技术方案提炼 1、2、3…条创新点，每条一句话、可独立成立，供代理人写权利要求。保护点宁窄勿空：写具体技术手段，不写「一种基于 X 的方法」这种空帽子。
   - **优点推导**：对应缺点逐条推导优点，因果链完整，不堆形容词。
   - **替代方案**：能实现同一目的的其他技术路径，有则写（有助于代理人圈定保护范围），没有写「暂无成熟替代方案」。
4. **附图。** 流程图、框图用黑白线框（模板通常要求黑白）。能用仓库已有图就用；没有则用文字详述占位并在 `review-needed.md` 列出待补图清单——交底书阶段图可后补，文字描述必须先达到「不看图即可明白方案」的标准。
5. **术语与命名统一。** 全文同一事物一个叫法（模板注意事项的通用要求）；写完通读一遍专查改名残留。
6. **事实回查。** 每个技术断言指向代码证据或用户确认；代码里没有、用户没说的实现细节一律不写，标注待用户补充。交底书里的数字（性能数据、参数值）必须有出处。
7. **交付。** 输出目录：交底书 `.docx`（副本）、事实来源记录、`review-needed.md`（待补图、待确认信息、待代理人核对的初评项）。

## 边界

- 不撰写权利要求书、说明书正式申请文本——那是代理人的工作，交底书止于技术披露。
- 不做授权率承诺；`patent-analysis` 的三性初评结论随附并标注「待检索确认」。
- 撰写过程中用户补充的技术要点记录进事实来源；AI 不代拟实现细节——技术方案里的每个步骤都要能回答「这是从哪来的」。

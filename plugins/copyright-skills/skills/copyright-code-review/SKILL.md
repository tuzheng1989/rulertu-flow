# 软著源代码合规预审

对拟申报的代码做提交前预审，消除可自检的客观驳回项。与 `software-copyright-cn` 互补：那个 skill 从仓库生成申报材料，本 skill 审查代码本身。预审通过不等于登记机关审查通过；登记机关审查中的比对结果无法本地复现，本地相似度自检（`similarity_check.py`）只能比对已知参考来源，其结果作为 C 项人工核验的证据输入，报告中如实标注。

## 口径声明

- 涉及登记的官方要求，一律以中国版权保护中心官网现行文本为准；本 skill 执行前须核对官网申请须知并留存核对记录（URL + 日期），无法核对的表述一律降级为内部口径，不写成官方规则。
- 本 skill 的「阻断」分级是内部暂停提交信号，表示按内部风控口径暂不申报、先整改，不是官方必驳规则。
- 核对记录：中国版权保护中心官网"所需文件"页（https://www.ccopyright.com.cn/index.php?optionid=1080），核对于 2026-09-03；登记填报入口为 https://register.ccopyright.com.cn （软件登记 R11）。

## 定位与边界（先读）

审查机关杜绝的是「不动脑筋让 AI 写代码」，不是「人类架构师让 AI 辅助开发」。本技能按后者定位工作：人掌握设计（架构、业务规则、验收标准），AI 在人的审批下实施，全程留痕。「辅助开发」与「不动脑代写」的分界不在谁敲键盘，落在流程上，本技能强制执行三道闸：

- **要点来自人**：每个待修模块的业务规则、特殊输入、失败模式由用户提供，不从代码反推、不脑补。
- **方案过人审**：修复建议先出清单，用户逐条批准后才动手。
- **结果过人验**：实施后用户验收，测试回归通过才算关闭。

硬规则只有一条：不做表面伪装——只换注释、换命名而不改变代码实质的手法不提供，那既过不了逻辑核验，也护不住知识产权。人的创造性投入体现在要点、审批、验收三个环节，全部留痕，争议时就是最有力的证据。

## 工作流

1. **确认审查对象。** 代码目录、软件名称、版本号、是否基于已有软件二次开发。名称版本必须与申请表、说明书、源代码文档完全一致；用户没给就先问，不用仓库值猜。
2. **运行自动扫描。** 脚本只做事实收集，结论由人工核验给出，脚本结果不直接当结论。
   - 客观缺陷：`python scripts/scan_source.py --repo <代码目录> --output <输出目录>/scan-report.json`，收集占位符、乱码、连续空行、第三方版权头、入口候选、空桩行。
   - 本地查重自检：把疑似来源（项目所用脚手架、模板、教程仓库的本地 clone）备到一个目录，运行 `python scripts/similarity_check.py --repo <代码目录> --references <参考目录> --output <输出目录>/similarity-report.json`（`--references` 可重复传多个）。脚本按 6 行窗口指纹比对，报告每个命中文件的包含度、最长连续相似行数和 `文件:行号 ↔ 参考文件:行号` 证据。没有疑似来源时跳过，并在预审报告中把「本地查重」列为未执行项。
3. **人工核验六大项。** 按下方清单逐项给 pass / fail，每条结论附证据（`文件:行号`）。脚本覆盖 B、C 两项的机械部分，A、D、E、F 和 B 的链路完整性必须人工读代码。
4. **输出预审报告。** 按下方格式写到用户指定目录。默认不改业务代码；用户确认后可进入修复模式（见下方「修复模式」）。

## 核验清单

### A 格式规范

- 软件名称、版本号在申请表、说明书、源代码文档中全程一致，签章信息无错配。
- 源代码文档：前 30 页 + 后 30 页、每页不少于 50 行、页眉标注软件名称/版本号/页码、顺序连贯。此项由 `software-copyright-cn` 生成时保证，预审只核对既有文档，不生成文档。

### B 逻辑完整性

- 主程序入口存在，且出现在源代码文档前部。
- 入口 → 模块调用 → 数据流转 → 结果输出链路完整闭环，无孤立功能片段、无断链调用。
- 无大量连续空行、无效注释、乱码、TODO/FIXME/待实现占位、空函数体、`NotImplementedError` 桩、未完成片段（脚本扫描后抽查确认，注意剔除字符串与文档里的误报）。

### C 权属合规

- 扫描第三方版权头、license 文本、`@author` 标记；命中即列出，要求移除或按来源标注。
- 引用开源代码：标注来源与许可协议，并说明实质性改动；仅原样复制未改的直接判阻断。
- 与常见脚手架、教科书示例、通用模板高度雷同的片段逐一列出，处理方式是改写为项目自有实现（换数据结构、换实现路径都必须服务于真实工程理由），不是表面换皮。
- 有 similarity-report.json 时：命中文件逐条人工比对，区分「有真实工程理由的自有实现」（保留）与「原样复制未改」（判阻断，进修复模式）；报告中的行号对直接作证据指针，相似≠抄袭，结论由人工给出。

### D 人创主导（核心项）

- 核心业务算法与关键模块是否体现项目独有内容：业务规则、自定义校验、特殊场景处理、异常与边界分支。缺失 → 进入「核心模块重写」流程（见修复模式），重写方向指向真实业务规则（这个系统到底要处理什么特殊输入、什么失败模式），不是换注释换命名。
- 注释抽查：注释是否说明业务场景、边界取值原因、问题处理记录；纯复述代码的模板注释标记删除或改写为有信息量的注释。
- 开发过程证据：Git 提交时间分布、迭代记录、开发笔记能否与代码对应。可作补正佐证，报告中提示用户保留，预审不核验真伪。

### E 衍生软件（仅二次开发场景）

- 逐条列出相对原软件的重要功能、性能或算法改进，每条给代码证据；只有界面调整、参数修改 → 判定不具备原创性，阻断。
- 提醒用户：需提交原著作权人授权文件，预审无法核验，列入待确认清单。

### F 材料联动

- 功能说明 500–1300 字（内部字数预算，非官方硬性要求），按「开发背景 → 核心功能 → 技术实现 → 应用场景」四段结构。
- 每个声称的功能给出代码证据指针（文件/函数）；无实现对应的功能声称 → 阻断（虚标功能是高概率补正/驳回风险，按内部口径暂停提交）。
- 操作手册/设计手册的模块划分、流程图节点与代码结构对应，截图来自真实运行界面。

## 输出格式

交付：`scan-report.json`、`similarity-report.json`（执行过本地查重时）+ 预审报告（markdown）。问题条目格式：

`[阻断|整改|建议] [A–F 类别] 文件:行号 —— 问题 —— 整改方向`

- 阻断：按内部口径暂停提交、先整改再申报（虚标功能与未标注的第三方代码是高概率补正/驳回风险，纯 AI 生成的核心逻辑同理）；阻断是本 skill 三级中最严重的一级。
- 整改：高概率触发补正（占位符、空行过多、页眉缺失）。
- 建议：降低查重与人工审查风险（注释质量、链路说明）。

报告末尾附「需用户确认/提供」清单：名称版本口径、衍生软件授权文件、开发过程记录。无法本地核验的项目（登记机关查重比对结果）如实标注为不可自检项。

## 修复模式

预审报告之后进入修复模式，按「建议 → 审批 → 实施 → 回归」四步走：

1. **建议**：把报告条目转成修复建议清单，每条含改动方案、影响面、验证方式、风险；阻断项排前。
2. **审批**：用户逐条批准 / 驳回 / 挂起；未批准的一律不动。
3. **实施**：每条单独改动、单独验证（编译/测试），不带无关改动。业务规则没讲清的先问，问不出来退回核心模块重写流程，不脑补。
4. **回归**：全部实施完重跑 `scripts/scan_source.py` 确认对应条目消除；交付实施记录（改了什么、为什么、怎么验证的），作为开发过程证据留存。

### 机械修复（方案明确，审批后直接实施）

- 折叠多余连续空行，清理无效注释；删除已解决的 TODO/FIXME 残留前，先确认对应工作确实已完成。
- 乱码：确认原编码后重新解码恢复；无法确定原文的标记为待人工确认，不瞎猜替换。
- 空桩行（`pass`、`...`）：异常分支里合法的保留，真桩位补实现。
- 材料格式问题（页眉、每页行数、文档顺序）交回 `software-copyright-cn` 重新生成，不在代码里修。

### 业务修复（需用户给业务输入，审批后实施）

- 通用实现替换为项目自有实现：换实现路径或数据结构，理由必须是真实工程约束（性能、边界、业务规则），不接受无理由换皮。
- 按系统真实的失败模式补异常处理、边界校验、日志；校验规则来自用户的业务，不来自通用最佳实践清单。
- 断链补全：孤立功能片段接入真实调用链，接不进来说明功能可疑，退回用户确认是否申报该功能。
- 模板注释改写为有信息量的注释：说明业务场景、边界取值原因、踩坑记录。

### 核心模块重写（纯 AI 实现、无设计痕迹的模块）

1. 与用户梳理该模块的真实业务规则、特殊输入、失败模式，落成书面要点；要点必须来自用户，不从代码反推。
2. 出重写方案：模块职责、接口约定、必须覆盖的业务分支、测试清单；用户批准后实施。
3. 实现后交用户验收：对照书面要点逐分支核对，测试回归通过，验收记录留痕。

人的创造性投入体现在要点、方案审批和验收三个环节——这是「辅助开发」区别于「不动脑代写」的地方，也是知识产权归属最直接的证据。

# 专利分析：从代码仓库挖掘可申报专利项

对代码仓库做可专利性分析，产出经用户确认的专利项候选清单。分析对象是**技术方案**，不是代码文本：同一仓库可能挖出零到多个候选，也可能一个都没有——没有就如实说，不硬凑。

## 审查标准（预筛依据）

预筛按《专利审查指南》现行版执行。开工前先核对版本：用户提供指南文档时以其为准；允许联网时检索最新版；都不行则按下列核心标准分析，并在报告中注明「按 2023 版指南核心标准，需代理人最终核对」。

- **客体（第 2 条第 2 款）**：方案必须是对产品、方法或其改进提出的新的技术方案。纯业务规则、纯界面呈现、纯数学公式、纯信息呈现不构成客体；算法/业务方法只有与具体技术功能结合、产生技术效果时才合格。
- **新颖性**：申请日前未公开（单独对比原则）。注意：已发表论文、已上线产品、开源公开、往期专利都可能构成现有技术；该风险必须逐项提示用户。
- **创造性（三步法）**：① 确定最接近的现有技术；② 确定区别特征和实际解决的技术问题；③ 判断对本领域技术人员是否显而易见。区别特征只有「常规技术手段的简单组合」时不可专利。
- **实用性**：能制造或使用，并产生积极效果。

## 工作流

1. **确认范围。** 仓库路径、技术领域、是否有已申报专利项/在申项目（避免重复）、分析重点模块。有在申项目的先把清单要来，直接排除。
2. **挖掘候选。** 通读仓库，关注这些候选信号：
   - 解决具体技术问题的自研算法或处理流程（不是调库）
   - 非常规的数据结构、索引、缓存或计算管线设计
   - 性能优化手段（有量化效果的优先）
   - 容错、重试、一致性、并发控制机制
   - 模块间或系统间的自研协议与协作机制
   - 资源调度、降级、限流等运行策略
   每个候选必须落到代码证据（文件/函数），没有代码证据的想法不列入。
3. **三性预筛。** 对每个候选逐项过：解决的技术问题（必须是技术问题，不是「用户体验不好」这类效果描述）→ 与你能想到的最接近现有技术的区别特征 → 区别特征带来的技术效果。任何一环讲不清就降级或剔除。客观性优先：把每个候选当成要被驳回的申请来挑毛病，不当成成果来包装。
4. **输出候选清单**（markdown），每项包含：

   `候选名称（建议）` / `技术问题` / `推定的最接近现有技术` / `区别特征` / `技术效果` / `代码证据（文件:行号）` / `三性初评（客体/新颖性/创造性/实用性，各给过/存疑/不过+理由）` / `公开风险（是否已论文、上线、开源）`

5. **用户确认。** 清单交给用户逐条决定进入撰写（对接 `patent-drafting`）、补充材料或放弃。两条硬提醒写进清单开头：**申请前不要公开技术细节**（发论文、开源、参展都构成现有技术）；分析结论是初筛，最终判断以专利代理人为准。

## 边界

- 不做侵权分析，不检索专利数据库（需要时建议用户走专业检索工具/代理人）。
- 区别特征的「最接近现有技术」只能推定，无检索支撑；报告中的新颖性/创造性结论一律标「初评」，不给「必授权」类判断。

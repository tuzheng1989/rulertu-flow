# 源代码 Word

## 注释口径（2026-09-08 起）

源代码文档**保留注释与空行**，按原始物理行逐字渲染；中文功能注释是审查要点——审查员看代码主要看功能逻辑是否对得上申报的软件名称，一行注释没有、全是英文变量名的代码很难判断原创性。原“构建层剥离注释与空行”口径（v1.2.0，已废止）：那是把“注释不计入行数”误解成“注释不能出现”的产物。

注释不占行数统计，但注释质量仍是预审对象：注释会进入提交文档，机器痕迹直接暴露。入选文件构建前须过 `scan_source.py` 十条 AI 特征注释检测（`md_markup`、`inline_code`、`section_ref`、`path_ref`、`halfwidth_paren_note`、`banner_divider`、`md_list`、`emph_phrase`、`req_id`、`ai_tool_marker`），并按人类注释习惯整改：

- 注释是纯文本，不写 Markdown 语法（加粗、标题井号、列表符号、链接、表格）。
- 不用反引号包代码名，代码名直接写。
- 不用元组式括号注堆叠补充说明，如 `(只写不读,P5-Q1)`；补充语义用自然语言或全角括号加完整句子。
- 不引用外部文档的精确坐标（`plan §2-W1.2` 一类）；确需交代出处时提文件名或内容主题，必要时标修改日期。
- 不写完整相对路径；提到具体文件用裸文件名。
- 长注释按整句分行，不在等宽处硬折行；换行落点跟句法走。
- 中文注释使用中文标点，不中英混排。
- 不用分隔线横幅（`====`、`----`）划分注释块；分节靠空行与一句概括。
- 注释里不写 Markdown 列表；并列信息用完整句子陈述。
- 不用强调性表达与需求管理黑话：不可绕过、唯一出口、绝不、严禁、红线、如实暴露一类。
- 需求编号（W/R/T/G/P 系，如 W4.1、R23、T16、G1、P5-Q1）连同解释性文字一并删除；运行时文案（报错、界面、API 出参）中的编号与文档坐标同样清除——文案结构与数值口径不变，只删编号。
- 严禁任何生成工具名或对话残留（Claude/ChatGPT/Copilot/Gemini/作为 AI 等）。
- 注释详略要有自然差异：不逐文件复制同一说明模板，多文件说明结构避免同构；此项机检盲区，构建前由人工或 `copy-polisher` 检测模式通读把关。
- 批次/阶段/实验分组词汇（“批次 3.3”“L1/L2/L3”“Treatment/对照”）删编号留约束；整改须保留项目连续性证据（模块间字段契约对应、端口/接口/阈值/降级规则等具体约束），禁误删。

精修改稿的操作细则以 `copy-polisher` 技能“源码注释审校”专节为准。**B=300 截断缓冲废止**：行数统计只看代码行，注释增删不影响截断边界，缓冲失去对象。

核对记录：行业经验清单《软著申报必查5项：源码与说明书避坑清单》（微信公众号「专技晋升干货库」，https://mp.weixin.qq.com/s/0pYFX1Wt5Noa2MoQ7SaDZg ，核对于 2026-09-08）——代码要有中文注释体现功能（本节）；代码/说明书无他人软件名、公司名、网址（copyright-code-review 扫描项）；说明书有界面截图与操作流程且与代码一致（manual.md）；软件名称与专业、业务方向对应（copyright-code-review 核验清单）。行数与页数口径沿用官网核对记录（见构建前检查节）。

## 统计口径（代码行）

“系统全部代码”指申请版本中由申请人编写并参与软件运行的源文件。默认纳入产品源码和必要启动脚本；默认排除测试、第三方依赖、vendor/minified 文件、构建产物、缓存、数据、模型、锁文件、文档、实验结果、生成代码、`.env` 和秘密文件。边界不明确时，把候选文件列入清单供用户确认，不静默删除。

先运行：

```powershell
python scripts/inventory_repo.py --repo . --output "code-inventory.json"
```

需要调整口径时使用重复的 `--include-root` 或 `--exclude`。行数达标一律按**代码行**统计：代码行 = 非注释、非空行的物理行（`strip_source.code_line_rows` 计算；docstring 按注释类不计，行尾注释所在行算代码行）。3,000 行阈值判断、前/后 1,500 段截取、登记表“源程序量”全部基于代码行口径。清单中的物理行数是仓库事实记录，供核对，不参与截断判断；不要为凑行数删注释或空行，也不要先删空行再计数。

## 抽取规则

- 代码行总数大于 3,000：按清单固定的文件路径顺序串接全部物理行，取**覆盖前 1,500 个代码行的物理行段**（首行至第 1,500 个代码行所在物理行）与**覆盖后 1,500 个代码行的物理行段**（第 total−1499 个代码行所在物理行至末行）；两段之间的物理行不提交，段内注释与空行随物理行一并保留。
- 注释精修在构建之前完成：截断边界由代码行决定，注释增删不移动边界，但精修本身要在构建前做完（见注释口径）。
- 主程序入口必须出现在文档前部：默认按清单文件路径顺序串接；入口未居前时，用 `--first <入口相对路径>` 把它前置到串接序列最前，manifest 的 `reordered_first` 字段记录本次前置的文件与顺序。入口候选由 `inventory_repo.py` 结果与用户确认共同确定。
- 代码行总数不超过 3,000：提交全部物理行。
- Word 左列显示 `相对路径:物理行号`（原始行号，注释与空行占行号）；文件名、页眉或分隔文字不占源码行数。
- manifest 双轨记录：`total_physical_lines`（原始物理行数）、`total_code_lines`（代码行数）、`strip_stats`（每文件分类计数）、`selected_physical_line_count` / `selected_code_line_count`、首行/前段末行/后段首行/末行及 SHA-256（selected_sha256 按选中物理行的 path/line/text 串接计算）。

## 构建前检查

入选文件先过静态扫描（主 SKILL.md 第 3 步）：占位符、乱码、第三方版权头、空桩行、AI 特征注释命中项经用户审批修复后才构建。扫描后置会让缺陷直接进入提交件，补正成本远高于构建前处理。

构建命令：

```powershell
python scripts/build_source_docx.py --inventory "code-inventory.json" --output "源代码.docx" --title "软件全称" --version "V1.0" --first "src/main.py"
python scripts/render_check.py --docx "源代码.docx" --min-lines 50 --output render-report.json
```

构建器按每页 50 个源码记录分页；提交页数以选中物理行数为准。每页 50 行对齐官方“每页不少于 50 行”口径（核对记录：中国版权保护中心官网"所需文件"页，https://www.ccopyright.com.cn/index.php?optionid=1080，2026-09-03）。长行在 Word 中折行显示，仍只对应一个源文件物理行，manifest 的记录数不变；但折行会使该页实际渲染行数少于每页记录数，`render_check.py` 的报告会列出实际行数不足 `--min-lines` 的页，整改（调小 `--lines-per-page` 或字号）由人工决策，构建器不自动改版式。本机无 soffice 时脚本非零退出并提示转人工，不伪造通过。

## 完成标准

- Word 中源码记录数等于 `selected_physical_line_count`；大仓库为前后两个代码行段覆盖的物理行，小仓库等于全部物理行。
- 中文功能注释覆盖关键代码：模块头、核心算法分支、业务规则处有能看出软件功能的注释；十条 AI 特征检测清零。
- 主程序入口出现在文档前部；用 `--first` 前置时，manifest 的 `reordered_first` 与文档首记录 `first.path` 一致可核。入选文件无占位符、乱码、第三方版权头和空桩行（构建前扫描已确认）。
- 前后段边界与代码行口径一致，无重复、漏段或排序漂移；manifest 的 `reordered_first` 如实记录任何前置调整。
- manifest 双轨行数可核：`total_code_lines` ≤ `total_physical_lines`，`strip_stats` 各文件代码行数之和等于 `total_code_lines`。
- 文档不含密钥、个人数据、第三方压缩库或与申请软件无关的实验资产。
- 软件名称和版本与登记表、说明书一致；页眉页脚和页码连续。
- 渲染实测：`render_check.py` 报告无不足页；本机无法渲染时把“逐页核对每页行数”列入 `review-needed.md` 人工核对项。

审计口径移交：说明书 audit JSON 的 `page_evidence` 键为“内容页序号（1 起）”，与 docx 物理页号相差封面+目录 2 页，消费时注意换算。

# 说明书 / 操作手册

## 叙事顺序

按真实用户完成任务的顺序组织，不按源码目录罗列：启动或登录 → 进入工作区 → 导入/选择数据 → 配置处理 → 执行核心功能 → 查看结果 → 质量检查或异常处理 → 导出/回放/审计。某一步在本系统不存在就删去，不补写想象功能。

每个功能页回答四件事：用户从哪里进入、做什么操作、界面出现什么结果、下一步去哪里。说明书正文使用第三人称或直接操作句，保持正式但自然。

## 图片证据

优先启动真实系统并沿上述动线截图。每张图保留稳定的窗口范围和一致缩放，图中出现的编号与正文步骤对应。裁掉桌面杂物、浏览器账户和开发者工具；遮蔽密钥、个人信息、内网地址和真实业务数据。不要使用 AI 生成的产品界面代替实际截图。

若仓库没有可运行界面：

1. 使用仓库已有架构图、流程图或命令行执行截图；
2. 必要时绘制基于代码关系的流程示意图，并在图题中写“示意图”；示意图节点对应真实代码模块，节点命名与代码模块或界面元素一致，不画抽象概念图；
3. 在 `review-needed.md` 记录缺少哪些真实界面图。

## Word 构建

创建 UTF-8 JSON 规格，结构见 `scripts/build_manual_docx.py --example`。运行：

```powershell
python scripts/build_manual_docx.py --spec manual.json --output "软件说明书.docx" --min-pages 10
```

构建器使用封面、目录说明和逐页内容单元保证至少 10 页。页面数量是下限，不要用空白页凑数；每页要有具体功能、操作、结果或必要图示。目录页可在 Word 中更新自动目录，也可保留构建器生成的静态目录。

## 文字审校

先完成有证据的技术草稿，再调用 `$humanizer` 改稿。要求它保留章节顺序、步骤编号、控件名、数据名、限制和所有数字，只修掉机械排比、空泛拔高、宣传口吻、重复解释及协作式结尾。不要把操作手册改成口语随笔。

## 完成标准

- 至少 10 页，并且功能顺序从入口到结果连贯。
- 正文中的每个按钮、页面、输入、输出都能在截图或代码中找到。
- 图片清晰、图题连续、正文有引用；同一张图不反复充页数。
- 软件名称、版本、完成日期口径与登记表一致。
- 在 Word 或导出的 PDF 中逐页检查，无孤行标题、图片截断或空白内容页。
